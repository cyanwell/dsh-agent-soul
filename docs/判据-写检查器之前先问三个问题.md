# 写检查器之前先问三个问题（2026-11-05）

> 为什么有这一页：2026-11-05 那一晚，我写的检查器**报错了三次**，
> 每一次都不是被检查的东西坏了，是**判据本身错了**。
>
> 三次都长同一个形状：**我看到一个现象，立刻把它当成了判据。**
>
> 这一页记的是那三次，以及从那三次里抽出来的三个问题。
> **下次写检查之前先问一遍，比读十条规范有用。**

---

## 问题一：这条检查报红时，我该信它吗？

### 踩过的那三次

| # | 我写的判据 | 它报了什么 | 真实情况 |
|---|---|---|---|
| ① | 「包在 bundles 里排在内置包之后 → 会被抢」 | 「两个 profile 都是 BAD」 | **那 22 个插件根本不注册服务**，不会被抢 |
| ② | 「pnpm 不在 PATH → 装不了」 | FAIL | 只挡 `dsh plugin add` 这条 CLI 路；**桌面端走 `install-desktop.ps1`，不经过 pnpm** |
| ③ | 「包根目录下要有 `client.js`」 | 「32 个包全缺」 | 客户端代码在 **`lib/client.js`**；那 32 个包当时都在正常工作 |

### 三次的共同点

**我都是从「一个看起来对的说法」出发的，没有先在一个已知健康的环境上验它。**

- ① 来自 `INSTALL.md` 的文字（那句话说的是「同名服务」先到先得，**不是「任何包」**）
- ② 来自「dsh 转发给 pnpm」这个事实（**转发**是事实，**只有这一条路**不是）
- ③ 来自「package.json 里 `dsh.client` 声明了客户端」（**声明了**是事实，**入口叫什么名字**不是）

### 为什么假警报特别坏

不是「多看一眼」的代价。真正的代价是：

> **下次真出问题时，我不信它了。**

一条永远红的检查，和一条永远绿的检查，**价值相同：都是零**。
而且红的更坏 —— 它会训练人忽略输出。

### 所以怎么问

> **「我把它拿到一个已知健康的系统上跑一遍，它会绿吗？」**

跑一次。**它红了，先怀疑判据，再怀疑环境。**

## 问题二：它抓不到的东西是什么？

### 反例

`verify-packaging.mjs` 有 136 条断言，全绿。**「全绿」证明了什么？**

只证明了「当时那些位置没有我描述的那个错」——**没有证明「出现那个错时它能抓到」**。

### 怎么验

**故意把错塞进去，看它报不报。**

2026-11-05 实测：

```bash
# 往 plugins/splash/cordis.patch.yml 里塞一个不存在的语法
echo "- update:" >> plugins/splash/cordis.patch.yml
node tools/verify-packaging.mjs
# → FAIL  patch 语法没写错（没有 update 键…）
#          plugins/splash/cordis.patch.yml: 用了不存在的 `- update:` 键
```

**它会报，而且指到具体文件。** 这才算这条检查成立。

### 一条检查的最小验收

| 步骤 | 做什么 | 判据 |
|---|---|---|
| ① | 在健康状态跑 | **必须全绿** |
| ② | 制造它该抓的那个错 | **必须红，且指到位置** |
| ③ | 恢复 | **必须回到全绿** |
| ④ | 连跑三次 | **输出逐字一致**（幂等） |

★ 第 ② 步最容易跳过 —— 因为「我刚写的，肯定对」。**恰恰是这一步能拆穿它。**

## 问题三：我查的是「存在」还是「有效」？

### 实例

`install-desktop.ps1` 的暂存自检，原来是：

```powershell
if (-not (Test-Path (Join-Path $stage $m))) { $missing += $m }
```

**一个 0 字节的 `client.js` 也能过。**

而 0 字节的客户端半和没有它**效果完全一样**：DSH 起不来 → `sanitizeProfile` → **抹掉用户的 bundles**。

**检查写对了形状（文件要在），没写对判据（文件要有内容）。**

### 这个形状的其他样子

| 「存在」的查法 | 坏在哪 |
|---|---|
| `Test-Path` / `fs.existsSync` | 0 字节也算在 |
| 「清单里写了 X」 | 清单和实际是两份东西（坑 6 就是这么发生的） |
| 「进程还在跑」 | 跑着不等于在工作 |
| 「接口返回 200」 | 200 可以是空 body |
| 「脚本退出码 0」 | 0 可以是它什么都没做 |

### 所以怎么问

> **「这条检查通过时，我能说出它到底确认了什么吗？」**

说不出，就是还在查「存在」。

## 附：一次真实的事故（`git add -A`）

2026-11-05 01:45，我在一个 commit 里用了 `git add -A`。

它收进去三个 `.db`：

```
%SystemDrive%/ProgramData/Microsoft/Windows/Caches/cversions.2.db
%SystemDrive%/ProgramData/Microsoft/Windows/Caches/{6AF0698E-...}.db
%SystemDrive%/ProgramData/Microsoft/Windows/Caches/{DDF571F2-...}.db
```

**来源是我自己的检查器** —— `checkPsPolicy` 在仓库根起了个 PowerShell 子进程，
某个未展开的 `%SystemDrive%` 被当成字面目录名，建出了那个目录树。

三件事：

1. **检查器自己会产副作用。** 它写文件的地方要选在不重要的位置（现在 `cwd: os.tmpdir()`）。
2. **`git add -A` 会把任何脏东西收进来。** 这次是缓存，下次可能是凭据。
   **add 要显式列路径。**
3. 清理要分两步：`.gitignore` 挡住未来的 + `git rm --cached` 清掉已有的。**历史不重写** ——
   那比留脏更危险。

## 一句话版本

```
写检查器之前：
  ① 拿到已知健康的环境上跑 —— 它绿吗？
  ② 故意塞个错进去 —— 它红吗？
  ③ 它绿的时候，我确认的到底是「存在」还是「有效」？
```

**三条都过，这条检查才算存在。否则它只是一行让人安心的输出。**
