两条入口

七条红线

01
L2 之外不许丢东西 —— 这是六层的地基
02
没有指针的摘要不许进 L4 —— 门牌失效 = ECHO 的唯一失败形状
03
检索只回指针 + 逐字片段，不做转述 —— 转述是二手污染
04
拿不到精确 seq 就给检索入口，绝不猜 —— 错的门牌比没有更坏
05
原文只追加，永不删改 —— 847/847 可回源的来源
06
哨兵只跟口径，不改布局 —— 它是观测面，不是层
07
别让两个地方同时是真相 —— 权威口径存在的全部意义

内存常驻方案：一手层解码进内存 待实施 L3 · L4 · L5
爀曦提出：把会话日志 / 一手层部分解码常驻内存，默认最近 3 天，预算 768 MB； 常驻天数与预算做进 ECHO 设置面板。
实测结论：3 天 = 212 MB（压缩比 3.2x），768MB 预算还剩 556 MB —— 装得下，而且宽松。

2026-10-23
L4 逐帧解码 —— 修掉「整个会话没进索引」 已落地 L4
现象：`memindex audit` 报 159 条摘要定位不完整，原因一律「日志解不开」； `verify` 直接抛 ERR_STRING_TOO_LONG。
根因：`decodeZstd()` 把全部帧 `Buffer.concat()` 成一个大 Buffer 再 `toString("utf8")` —— 而某个日志压缩后 212.5 MB，解压后**远超 Node 的 512 MB 字符串上限**。
真正代价：那个日志就是会话 session-1099f531 从 09-29 至今的完整记录，一直没进索引。
展开：修法与复验

修法：改成「逐帧解码 → 逐帧按行切 → 累积行」，内存里永远不出现完整的巨串； 单行超 8 MB 丢弃并计数，单帧解不开跳过并计数。

2026-10-23
L0 时钟权威源修复（`state.json` 停更一个月） 已落地 L0
现象：`hub\state.json` 的 `lastTurnAt` 停在 2026-09-27，而 SELF.md「距上轮 37076 分钟」正是从它读的。
根因：没有任何东西在写这个文件（`memq mark` 没人跑），而 `echo-doctor` 算出不一致却把 `status` 硬写成 "ok"。
修法：`self.mjs` 每次装配写 `lastSelfAt` + `selfRuns` 递增；SELF.md 那行改成 「最后一条手写状态距今：N 天（★ 这不是时钟）」。
展开：一个读法的坑

★ 关键判断：`lastTurnAt` 的语义是「最后一条手写状态」，不是时钟。 之前它被读成「系统停了一个月」，是读法错，不是数据错。

★ 另一个：`lastSelfAt` 原来用 `toISOString()` 写成 UTC，+08 下会显示 05:03 而本地 13:03 —— 已改本地时间。
