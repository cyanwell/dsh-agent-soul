# 架构：为什么它不能是插件

> 爀曦 2026-11-07 01:31 原话：
> 「为什么要解耦，因为 **DSH 的更新总是破坏兼容**，而且我想让 agent soul
> **能无脑接入不同的 harness（z code / codex 等）**，所以我们**不能作为任何一个 harness 的插件**，
> 而是**作为软件独立更新**。」

## 一、两条约束，一条推论

| # | 约束 | 推论 |
|---|---|---|
| 1 | harness 更新会破坏兼容 | **不能跟它的版本走** → 依赖面要小到「只用协议，不用 SDK」 |
| 2 | 要接多个 harness | **不能只服务一个** → 接口必须是通用的，不能是某个宿主的形状 |

★ **合起来推出一条硬规则：agent-soul 不 import 任何 harness 的包，只讲协议。**

## 二、谁提供什么

```
┌─────────────────────────────────────────────┐
│  agent-soul  （独立软件，自己发版）           │
│                                             │
│  ★ 核心 —— 这些是别人没有的，也是真正值钱的   │
│     · 会话存储（写入即索引）                  │
│     · 全文索引与检索                         │
│     · 人格层（SELF / USER / 长期约定）        │
│     · 事件层（心跳 / 唤醒 / 判定）            │
│                                             │
│  ○ 可选 —— 别人也有，只是它也能提供           │
│     · LLM 调用                              │
│     · 工具执行                               │
│     · 回合驱动                               │
└──────────────────┬──────────────────────────┘
                   │  适配器（薄层，一宿主一个）
       ┌───────────┼───────────┬──────────┐
       ↓           ↓           ↓          ↓
      DSH       z code       codex      别的
   （提供 LLM / 工具 / 回合 / UI）
```

**关键：核心跑在自己的进程里，宿主只是「调用方」。**

宿主升级了，最坏情况是适配器要改 —— 那是百来行，不是八万行。

## 三、三种运行模式

| 模式 | 谁驱动回合 | 用在什么时候 |
|---|---|---|
| **attached（默认）** | **宿主** | 挂在 DSH / codex 上时。agent-soul 只答「这段历史是什么」「这个记忆在哪」「这轮该注入什么」 |
| **standalone** | 自己 | 没有宿主、或者要一个纯 CLI 的时候 |
| **headless** | 外部脚本 | 被别的程序当库调（`import` 或 HTTP） |

★ **attached 是主路径。** standalone 是兜底，不是目标。

## 四、接入方式：为什么选 MCP

「无脑接入」的判据是：**换一个 harness，改动量应该是「填一个地址」，不是「改代码」。**

| 方式 | DSH | codex | z code | 判据 |
|---|---|---|---|---|
| **MCP** | ✅ | ✅ | 大概率 | **一份实现，多宿主可用** |
| HTTP + OpenAPI | 要写适配 | 要写适配 | 要写适配 | 每换一个都要写 |
| 各家的插件 SDK | ✅ | ✅ | ✅ | **违反约束 1 —— 跟版本走** |
| 命令行 | ✅ | ✅ | ✅ | 只能单向，拿不到宿主状态 |

★ **所以主推 MCP，HTTP 作为第二条腿（给不支持 MCP 的宿主）。**

## 五、MCP 要暴露什么

**只暴露「核心」那四样 —— 不暴露 LLM 和回合，因为宿主自己有。**

| 工具 | 作用 |
|---|---|
| `soul_recall` | 按关键词检索历史（跨会话、跨帧） |
| `soul_frame` | 取某会话某帧的原文 |
| `soul_remember` | 往人格/长期记忆里写一条 |
| `soul_persona` | 取当前人格层全文（宿主拼进 system prompt） |
| `soul_session_new` | 开一个新会话容器（宿主可以把它的会话 id 映射进来） |
| `soul_index` | 把宿主产生的一帧写进索引（**关键：宿主写什么，索引就跟什么**） |

★ **最后那个是关键** —— 挂载模式下，会话是由宿主产生的（它有自己的日志格式），
agent-soul **不抢存储**，而是接受宿主推过来的每一帧，自己建索引。

这样：**宿主换格式，我只改一个解析函数；我的索引永远在。**

| `web/server.mjs` | ✅ 留，作为 HTTP 适配器的基础 |
| `web/shell.html` | ✅ 留，作为「没有宿主 UI 时」的界面 |
| **`adapters/mcp.mjs`** | ★ **新增，这是主路径** |

## 七、一条不能忘的判据

**每次想往 agent-soul 里加东西，先问：这是「别人没有的」还是「别人也有的」？**

- 别人没有的 → 加进核心
- 别人也有的 → 别加，让宿主提供，适配器去接

★ 这条判据就是「解耦」本身。违反它的每一次，都是把绳结又系紧一圈。
