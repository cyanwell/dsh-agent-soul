## ① 多实例共享数据目录时，search 看不到别的实例写的帧

**触发**：两个 `SessionStore` 指向同一个 `dataDir`（比如服务端一个、测试脚本一个），
A 实例 `append()` 之后，B 实例 `search()` 命中 0。

**实测**：`tools/live-smoke.mjs` 的「写入即索引」项，2026-11-07 命中 0 复现。

**根因**：每个实例各有一份 `this.ix`（内存索引）和 `this.cache`（会话缓存）。
`load()` 有 stat 指纹（`size:mtime`）能发现外部改动，
但 **`list()` 和 `buildIndex()` 没有** —— 它们只信自己的内存状态。

**为什么现在不修**：要修得重做索引失效粒度（按会话 fingerprint 而不是整实例），
那是 `store.mjs` 的一次结构性改动。而当前的使用形态（一个进程一个实例）不受影响。

**什么时候必须修**：真要做多进程写入（比如 MCP stdio + HTTP 两条腿同时写同一个目录）时。

★ **对 MCP 用户的实际影响**：stdio 和 HTTP 两个适配器如果各自起一个 store，
  在 stdio 里写的帧，HTTP 那边搜不到。**当前两条腿都指向同一个 `dataDir`，所以这个坑是热的。**

## ④ ~~关掉启动器之后，服务进程还活着~~　✅ **已修（2026-11-07）**

**症状**：双击 exe → 起服务 → 关掉命令行窗口（或从外部 kill 掉 `agent-soul.exe`）→
**node 服务进程还在跑**。再双击 exe，报：

```
解压失败（载荷起点 9750）：文件 C:\Users\pc\AppData\Local\agent-soul\runtime\node.exe
正由另一进程使用，因此该进程无法访问此文件。
```

而那个孤儿进程**还把整个解压目录锁住** —— 连改名都做不到（EBUSY）。

**实测证据（2026-11-07 03:09）**：
```
node.exe 进程 6 个：
 ★ PID 10312
     exe C:\Users\pc\AppData\Local\agent-soul\runtime\node.exe
     cmd "...\agent-soul\runtime\node.exe" "...\agent-soul\src\index.mjs"
```
杀了它之后，目录立刻可清理、exe 立刻能再起。

**根因**：C# 启动器 `Process.Start(node, ...)` 起的是**子进程**。
启动器退出 ≠ 子进程退出 —— Windows 上默认不连带，除非用 Job Object 绑成一组。

**为什么这条最要命**：它出现在**用户最常做的那条路径上**。
「关掉窗口」是所有人的第一反应，而这一关就留下一个看不见的进程 +
一个锁住的目录，第二次双击直接失败，报错还指向一个他根本没碰过的文件。

**现在没修的原因**：修它要给启动器加 Job Object
（`CreateJobObject` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` + `AssignProcessToJobObject`），
是 C# 侧的一次真改动，不是调参数。**记在这里，不假装它不存在。**

### ★ 已修（2026-11-07）—— 两条腿一起上

**修法 1：Job Object（C# 侧）**
`build/Launcher.cs` 里已经加上：
```
CreateJobObject + JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE + AssignProcessToJobObject
```
启动器退出 → Job 关闭 → 子进程被系统杀掉。

**修法 2：父进程看门狗（node 侧，兜底）**
`src/util/parent-watchdog.mjs` —— 启动器把 `AGENT_SOUL_PARENT` 传给 node，
node 定期检查那个 PID 还在不在，没了就自己退。

★ **为什么两条都要**：Job Object 依赖启动器「正常退出」。
如果启动器是被 `TerminateProcess` 硬杀的，Job 句柄可能来不及关 ——
而看门狗不依赖任何人做好事，它自己看。

**实测**：kill 启动器 → node 跟着死，解压目录立刻可清理。

**当年的临时绕法**（留着，万一哪天又坏）：
```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.ExecutablePath -like '*agent-soul*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

## ⑤ 解压失败时的报错不够可执行

现在只说「文件正由另一进程使用」。应该说清三件事：
① 是哪个文件 ② 大概是哪个进程 ③ 三条可走的路。
★ 这一条和 ④ 是同一个病的两种表现：**④ 让问题发生，⑤ 让问题难查。**

## ⑥ Windows：`0.0.0.0:P` 和 `127.0.0.1:P` 能同时绑上，而且更具体的那个先接

**实测（2026-11-07，chat agent 抓的）**：服务绑 `0.0.0.0:8899` 报成功，
但本机 `127.0.0.1:8899` 拿到的是**老 TTS** 的 `{"ok":false,"err":"not found"}`，
而手机走局域网 IP 会连到新服务。

**本机坏、手机好 —— 最难查的那一种。**

★ 为什么难查：`listen()` **没报错**。两套绑定在 Windows 上是合法并存的，
路由由「更具体的那条」优先。所以你看到的是「服务起来了」+「本机访问返回别人的东西」，
而这两件事同时为真。

**防法**：绑完用 `127.0.0.1` 打自己一刀，应答不是自己就发警告。
`startMobileChat` 里已经这么做了（`verifyMyself()`，只警告不阻断 —— 因为
「本机被别人占」不影响手机用，阻断反而是错的）。

**当前占用的端口（2026-11-07 实测）**：8898 = 老 chat 插件（在 DeepSeek Harness.exe 进程内，绑 0.0.0.0）；
8899 = 老 TTS（绑 127.0.0.1）。所以新软件默认用 **8901**。

## ⑦ 思考退化器官：四条判据里只有「上下文水位」一条在真工作

**触发**：看 `/api/organs` 的第 6 张卡。不管有没有宿主连上、跑多少轮，它基本都停在
`0 / 4`（水位过 60% 时是 `1 / 4`）—— 因为**它拿不到能判的那几个数**。

**实测（2026-11-07，读 `D:\AI\dsh-tools\dsh-agent-soul-bridge\index.js` 原文，不是听说的）**：

| 字段 | 桥实际发的 | 出处 |
|---|---|---|
| `outputTokens` | **恒为 `null`** | `index.js:243` `outputTokens: null, // 没接` |
| 桥自己怎么交代 | hello 里带 `meta.notWired: ['outputTokens']` | `index.js:215` |
| `turnId` | `'dsh-' + sid.slice(0,8) + '-' + st.step`，而 `st.step += 1` 就在**每次上报前** | `index.js:235` / `:242` |
| 什么时候上报 | 借 `systemPrompt.context` 的 `render` 钩子 —— 每组装一次提示就报一次 | `index.js:452-467` |

**这两件事各自打断一条判据**：

- `outputTokens === null` ⇒ 器官**不动任何计数**（`degradation.mjs:226`，故意的：
  「拿不知道去充数就是骗人」）。于是「连续零输出」和「连续低产出」两条**永远不会触发**。
- `turnId` 每次上报都变 ⇒ 器官每次都判「这是新一轮」（`degradation.mjs:203`），
  `sameTurnSeen` 恒为 1；而「同轮膨胀」要求 `sameTurnSeen >= 2`（`:249`）
  ⇒ 第三条**也永远不会触发**。

**剩下能工作的只有上下文占比这一条**，而它按设计**单独最多到 watch、永远不建议中断**
（`degradation.mjs:19-20`：「它不是退化，它是退化的条件」）。

所以卡上那个 `0 / 4` **不是「它很健康」，是「三个症状一个都没在测」**。
`blind`（什么都读不到）那条兜底也接不住 —— 水位读得到时 `blind` 就是 false。

**★ 定性：这是「没接线」，不是「能力缺失」。** 差别很实在：

| | 现状 |
|---|---|
| **能力** | 在。判据、计分、证据清单、档位都写好了，`node tools/degradation-selftest.mjs` **46 通过 / 0 失败** —— 喂假数据进去，四条判据都能出结论。 |
| **接线** | 没接。宿主那侧没把 `outputTokens` 和「真正的轮次标识」交出来。桥的注释自己写着「不读宿主内部消息，宁可空着」——**是选择空着，不是拿不到**。 |

**为什么现在不修**：要真数据就得让桥去读宿主内部的每轮 usage，
那是 DSH 插件侧的一次真改动，而且要重启宿主才验证得了 —— 桥本身现在还卡在那一步上。

★ 在那之前**宁可让字段空着**，也不要拿「工具调用次数」之类的代理数去冒充 `outputTokens`：
那会把一条哑掉的判据，换成一条会撒谎的判据。

**什么时候必须修**：桥接插件接上真实 usage 的那一刻。届时要**同时**改两件事 ——
① `outputTokens` 填真值；② `turnId` 改成「同一轮内不变」的标识（它现在其实是上报序号）。
只改 ① 的话，「同轮膨胀」那一条仍然是哑的。

## ⑧ `log:<sid>#seq=n` 里的 n 有两种口径（2026-11-11 已修解析；限制仍在）

**触发**：拿 cleanup 回执 / 压缩门牌去 `soul_open`，内容对不上预期 —— 门牌能打开、也返回 200，
但那是**另一帧**的原文。

**根因**：同一个会话里有两个都在递增的帧号：

| 口径 | 落在哪 | 谁在用 |
|---|---|---|
| **宿主原帧号**（DSH 的 seq） | `frames[i].meta.seq`（`toFrames` 原样带过来） | pruner 的起止 seq、cleanup 回执门牌、压缩门牌 |
| **容器帧号**（本软件 append 分配） | `frames[i].seq`（1,2,3…，含帧 0） | 内部帧、`soul_frame`、旧测试 |

**实测（2026-11-10/11，`tools/query-open-selftest.mjs` ①a–①d）**：构造容器 seq 1/2/3 ↔ 宿主 seq 901/1/902，
门牌 `#seq=1` 下两帧原文不同 —— 旧口径（只按容器 seq 查）取到「HOST-901」，
正确目标是「HOST-1（容器 seq=2）」。**两个都合法、都返回 ok**，所以它不是崩溃，是静默取错。

**现在的规则**（`src/tools/query.mjs` 的 `resolveLogFrame`，`open` 与 `soul_open` 共用）：

1. 先精确匹配 `meta.seq === n`；
2. 没有 meta 命中才回退容器 `seq === n`（旧内部帧兼容）；
3. 多个宿主帧同号但**内容不同** → `AMBIGUOUS_LOG_PTR` + 列候选，**不返回正文、不替你选**；
4. 返回里永远带 `matchedBy` / `containerSeq` / `hostSeq`，取的是哪一路可核对。

**仍未解决的限制**：

- **同一内容被重复回放**（重复 `meta.seq`，实测有过 392 条）时只按「类型 + 原文」判同一帧 ——
  如果两帧内容完全一样、只是 `t` 不同，取到哪条都返回同一段原文，但**返回不了「哪一次是原始的」**。
- 歧义时只能人工按 `containerSeq` 用 `soul_frame` 精确取 —— **这一步没有自动仲裁**。
- `index.jsonl` 里的 text 仍是 500 字截断版（写索引时的取舍，见 `store.mjs:690-702`）；
  `open` 已经不走它，但**别的读索引的路径仍然只能看到截断版**。
- 宿主 pruner 仍是桩时，cleanup 回执根本拿不到（`stage=stub`），这条限制与门牌解析无关。
