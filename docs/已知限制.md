# 已知限制

> 这一页只放**已经确认存在、但现在没修**的限制。每条都带实测证据和触发条件。
> 不是「以后再说」，是「现在说得清」。

## ① 多实例共享数据目录时，search 看不到别的实例写的帧

**触发**：两个 `SessionStore` 指向同一个 `dataDir`（比如服务端一个、测试脚本一个），
A 实例 `append()` 之后，B 实例 `search()` 命中 0。

**实测**：`tools/live-smoke.mjs` 的「写入即索引」项，2026-11-07 命中 0 复现。

**根因**：每个实例各有一份 `this.ix`（内存索引）和 `this.cache`（会话缓存）。
`load()` 有 stat 指纹（`size:mtime`）能发现外部改动，
但 **`list()` 和 `buildIndex()` 没有** —— 它们只信自己的内存状态。

**为什么现在不修**：要修得重做索引失效粒度（按会话 fingerprint 而不是整实例），
那是 `store.mjs` 的一次结构性改动。而当前的使用形态（一个进程一个实例）不受影响。

**什么时候必须修**：真要做多进程写入（比如 MCP stdio + HTTP 两条腿同时写同一个目录）时。

★ **对 MCP 用户的实际影响**：stdio 和 HTTP 两个适配器如果各自起一个 store，
  在 stdio 里写的帧，HTTP 那边搜不到。**当前两条腿都指向同一个 `dataDir`，所以这个坑是热的。**

## ② 首发版 exe 的 config.json 里 dataDir 仍是绝对路径

**实测**：从 `build/agent-soul.exe` 启动，横幅打的是 `数据 D:/AI/agent-soul/data` —— 
那是开发机的路径，不是 `%LOCALAPPDATA%\agent-soul\data`。

**已做**：`src/config.mjs` 加了 `appRoot()` + `resolvePath()`，支持相对路径；
`config.release.json` 里 `dataDir` 写的是 `data`。

**待做**：打包时用 `config.release.json` 而不是 `config.json`。

## ④ 关掉启动器之后，服务进程还活着（★ 今晚实测撞了两次）

**症状**：双击 exe → 起服务 → 关掉命令行窗口（或从外部 kill 掉 `agent-soul.exe`）→
**node 服务进程还在跑**。再双击 exe，报：

```
解压失败（载荷起点 9750）：文件 C:\Users\pc\AppData\Local\agent-soul\runtime\node.exe
正由另一进程使用，因此该进程无法访问此文件。
```

而那个孤儿进程**还把整个解压目录锁住** —— 连改名都做不到（EBUSY）。

**实测证据（2026-11-07 03:09）**：
```
node.exe 进程 6 个：
 ★ PID 10312
     exe C:\Users\pc\AppData\Local\agent-soul\runtime\node.exe
     cmd "...\agent-soul\runtime\node.exe" "...\agent-soul\src\index.mjs"
```
杀了它之后，目录立刻可清理、exe 立刻能再起。

**根因**：C# 启动器 `Process.Start(node, ...)` 起的是**子进程**。
启动器退出 ≠ 子进程退出 —— Windows 上默认不连带，除非用 Job Object 绑成一组。

**为什么这条最要命**：它出现在**用户最常做的那条路径上**。
「关掉窗口」是所有人的第一反应，而这一关就留下一个看不见的进程 +
一个锁住的目录，第二次双击直接失败，报错还指向一个他根本没碰过的文件。

**现在没修的原因**：修它要给启动器加 Job Object
（`CreateJobObject` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` + `AssignProcessToJobObject`），
是 C# 侧的一次真改动，不是调参数。**记在这里，不假装它不存在。**

**临时绕法**（写在这里，让撞上的人有路走）：
```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.ExecutablePath -like '*agent-soul*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

## ⑤ 解压失败时的报错不够可执行

现在只说「文件正由另一进程使用」。应该说清三件事：
① 是哪个文件 ② 大概是哪个进程 ③ 三条可走的路。
★ 这一条和 ④ 是同一个病的两种表现：**④ 让问题发生，⑤ 让问题难查。**

## ⑥ Windows：`0.0.0.0:P` 和 `127.0.0.1:P` 能同时绑上，而且更具体的那个先接

**实测（2026-11-07，chat agent 抓的）**：服务绑 `0.0.0.0:8899` 报成功，
但本机 `127.0.0.1:8899` 拿到的是**老 TTS** 的 `{"ok":false,"err":"not found"}`，
而手机走局域网 IP 会连到新服务。

**本机坏、手机好 —— 最难查的那一种。**

★ 为什么难查：`listen()` **没报错**。两套绑定在 Windows 上是合法并存的，
路由由「更具体的那条」优先。所以你看到的是「服务起来了」+「本机访问返回别人的东西」，
而这两件事同时为真。

**防法**：绑完用 `127.0.0.1` 打自己一刀，应答不是自己就发警告。
`startMobileChat` 里已经这么做了（`verifyMyself()`，只警告不阻断 —— 因为
「本机被别人占」不影响手机用，阻断反而是错的）。

**当前占用的端口（2026-11-07 实测）**：8898 = 老 chat 插件（在 DeepSeek Harness.exe 进程内，绑 0.0.0.0）；
8899 = 老 TTS（绑 127.0.0.1）。所以新软件默认用 **8901**。
