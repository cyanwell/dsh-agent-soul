# 安装常见问题汇总与解决方法

> 这份文档来自**一台真实机器的完整安装过程**（2026-10-23，Windows / DSH 0.2.1-rc.2 / Electron 44.7.0 / node 24.21.0）——
> 不是推演出来的清单，是那个人一条一条撞出来的。
>
> `INSTALL.md` 讲**怎么装**；这份讲**装不上、装上了但没数据的时候怎么办**。
>
> ★ 先读这一句，能省掉一半排查时间：
> **这套架构里最麻烦的故障不报错。** 插件加载成功、界面在、路由在，只是里面**没有数据**。
> 所以你遇到的问题如果长成「这一项空的」，请直接跳到 [第三节](#三装上了但某一项是空的)，不要在「插件是不是没装上」上耗时间。

## 零、先跑这三条，多数问题当场定位

```powershell
# ① 体检（最有用的一条，16 项一次看完）
node <kit目录>\echo\echo-doctor.mjs --soul "<书房根>" --memory "<记忆根>" --sessions "<DSH_HOME>\sessions"

# ② 零件清单
#    （在 DSH 会话里让 agent 调 agent_soul_install verify，或看 INSTALL.md 的命令行方式）

# ③ 装到哪了、版本对不对
#    （在 DSH 会话里让 agent 调 agent_soul_install status）

# ④ 注册 id 有没有撞车（★ 2026-10-24 新加；「启动就崩」先看这条）
node <仓库根>\tools\verify-client-ids.mjs
#    退出码 0 = 没有重复，1 = 发现重复（会列出「哪两个包撞在同一个 id 上」）
```

★ **第 ④ 条是给「DSH 一启动就崩」准备的。** 那种崩法症状很吓人（弹崩溃恢复对话框、
点「停用所有插件」还会把配置清空），但根因往往只是两个插件用了同一个注册 id ——
见 [第二节](#二启动就崩--反复崩溃循环最急的一类)。

**看体检结果的方式**：`✓` 是通过，`!` 是警告（多数是「可选未装」），`error` 才是真坏。
★ 如果你看到一堆 `!` 但**没有 error**，**架构是成立的** —— 那些是设计上允许空着的项，不是故障。

## 一、装之前就挡路的

### 1.1 安装脚本说找不到 node

**症状**：`install-desktop.ps1` 跑到第二步就退出，打印 `node.exe not found`。
而你明明装了 DSH，也明明能跑起来。

**为什么**：旧版脚本只在 `%LOCALAPPDATA%\Programs\DeepSeek Harness` 下找 node，找不到再看 PATH。
**但如果 DSH 装在别的盘（比如 `E:\dsh`），或者你用的是别的方式装的，这两处都没有。**

**解决**（任选一）：

```powershell
# 方式 A：直接告诉它 node 在哪（最省事）
$env:DSH_NODE = "E:\dsh\resources\runtime\primary-runtime\dependencies\node\bin\node.exe"
.\install-desktop.ps1

# 方式 B：自己找一下 DSH 自带的 node
Get-ChildItem "E:\dsh\resources\runtime" -Recurse -Filter "node.exe" | Select-Object -First 3
```

★ **注意 `E:\dsh\resources\runtime\bin\node.exe` 可能不存在，那里只有 `node.cmd`** ——
真实的 node 在 `resources\runtime\primary-runtime\dependencies\node\bin\` 下面。

★ 如果脚本是**新版**的（2026-10-23 之后），它会自动按「`DSH_NODE` → 从 profile 上推安装根 → 常见位置 → PATH」试一遍，
都找不到时会**列出它试过哪些路径**，照着那个列表补一个就行。

### 1.2 脚本要下载东西，但出不了网

**症状**：`Invoke-WebRequest` 或 `curl` 返回 `http_code 000`，或者一直卡住。
而 DSH 里的 `web_fetch` 却能访问同一个地址。

**为什么**：有些机器的 TLS 被安全软件切断，只放行特定程序。

**解决**：
- 用**本地已有的备份**当安装源（如果你之前备份过 `soul-kit` 目录）
- 或者让 DSH 会话里的 agent 用它的 `web_fetch` 帮你下载，再手动放进 kit 目录
- ★ 不要为此关掉安全软件 —— 换一条路比重开一个洞好

### 1.3 桌面端拒绝 `dsh plugin add`

**症状**：`EPERM`，或者报 `managed exclusively by the Electron application`。

**为什么**：桌面端的 profile 是它自己管的，CLI 不能直接改。

**解决**：
- **手动写 profile 的 `package.json`**（`dsh.profile.bundles` 加包名、`dependencies` 加 `file:` 路径）
- 或者用仓库里的 `tools/add-bundle.cjs`
- ★ 改完之后**一定要用 node 的 `JSON.parse` 验一遍**，不要用 PowerShell 的 `ConvertFrom-Json` ——
  后者容忍 BOM，会给你假通过；而 DSH 启动是直接 `JSON.parse`，带 BOM 就崩

## 二、启动就崩 / 反复崩溃循环（最急的一类）

> **这一类先看，因为它会连累你的整个配置。**
> 2026-10-22 ~ 10-24 收到三份真实反馈，其中两份的崩溃都出在这里。

### 2.1 DSH 每次启动都崩，弹出崩溃恢复对话框

**症状**（那种一整页崩、让你选「停用所有插件」的）：

```
Error: web boot: 1 entry did not activate
xxx: import failed
    at .../app.asar/lib/main.js:12437:15
```

打开崩溃报告（`%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-*.log`）往下翻，通常还能看到两行之一：

```
client-modules: duplicate factory registration for "某个-id"
  (bundle executed twice without invalidate?)
```

```
loaded without registering "某个包名" via __ModuleLoader__.load
```

**根因**：**两个东西用同一个 id 注册了客户端模块。**

客户端半的 `__ModuleLoader__.load({ id })` 里那个 `id` 是 factory 的键。
第二个包用同一个 id 去注册，**直接抛异常 → 整个 entry 不激活 → web boot 失败 → 弹崩溃恢复**。

**★★ 为什么这件事特别要紧**：如果你点了「停用所有插件」，宿主会把
`dsh.profile.bundles` 重写成 web 模板的 2 项、并把 `cordis.patch.yml` 清空 ——
**于是每重启一次，装好的插件就掉一批。** 这是宿主的 `sanitizeProfile` 行为，
不是本仓库的代码，但知道它能救你的配置。

**先做这一步（保住配置）**：

```powershell
# 崩溃对话框出现时，先把配置备份一份，再决定点不点那个按钮
$p = "<你的 DSH_HOME>\profiles\<profile名>\package.json"
Copy-Item $p "$p.bak-crash" -Force
```

**然后诊断（这条能直接告诉你撞的是谁）**：

```powershell
node <仓库根>\tools\verify-client-ids.mjs
```

输出形如：

```
  id = "dsh-yanqing-echo"
    被 2 个不同的包同时占用：
      pkg=dsh-agent-echo
        ...\node_modules\dsh-agent-echo\client.js
      pkg=dsh-yanqing-echo
        ...\node_modules\dsh-yanqing-echo\client.js
```

**修法二选一**：

- **旧包不再需要** → 从 `node_modules` 里删掉它，并从 `dsh.profile.bundles` 里去掉那一项（用 node 改，别用 PowerShell 的 ConvertFrom-Json）
- **两个都要留** → 让各自的 `client.js` 用自己的 `package.json` 里的 `name` 当 id

★ **判据**：改完再跑一次 `verify-client-ids.mjs`，退出码必须是 0；然后**重启 DSH**
（客户端入口图是启动时一次性组合的，刷新页面不够）。

**★ 这不是「id 必须等于包名」的审美问题**，是 **id 必须全局唯一**。
包名天然唯一，所以 `id := package.json.name` 是最省事的做法。

### 2.2 只是某个面板不见了，DSH 没崩

**这和 2.1 是两件事，别混。**

如果只是侧边栏少了一项、或者某个面板空白，**DSH 本身能正常起来、其他功能都在** ——
那多半是这个插件的入口报错被吞了，不是 id 撞车。

```powershell
# 打开 devtools 控制台（Ctrl+Shift+I），看有没有这条
#   loaded without registering "xxx" via __ModuleLoader__.load
```

**有这条** → 是 id 对不上，按 2.1 查。
**没有这条、控制台一片干净** → 那是另一个经典坑：`exports.inject` 没写
（详见仓库 `README` 里「插件装载的静默杀手」那一节）。

### 2.3 `agent_soul_verify` 报 `Command failed: ...exe ...diagnose.mjs --json`

**症状**：调用体检工具，回一句

```
Command failed: DeepSeek Orb.exe .../kit/echo/diagnose.mjs --json
```

**根因**：这个工具跑在 Electron 宿主里，`process.execPath` 是
`DeepSeek Orb.exe`，**不是 node**。它不认 `--json`、也不会去执行一个 `.mjs`。

**已修（2026-10-24）**：现在会按四级候选找 node（`ECHO_NODE` → `NODE` →
`execPath`（仅当它真的是 node）→ `node`（PATH）→ 常见安装路径）。

**如果你还在旧版本上，或者四个候选全失败**，直接指定：

```powershell
$env:ECHO_NODE = "C:\Program Files\nodejs\node.exe"   # 换成你机器上真 node 的路径
```

★ 新版失败时会把**每个候选的 exit 和错误全打出来**，
不会只说一句「一行输出都没有」——照着那张表看哪个 ✗ 卡在哪一步。

### 2.4 体检报「推送层 SELF 读不到」，但 GUI 里明明看得到 SELF

**这是假红**，而且我们为它改过三版才改对。

**最快的判据**（不用信体检，自己看）：

```powershell
# 直接把 doctor 跑一遍，看 self 这一项
node <kit目录>\echo\echo-doctor.mjs --soul "<书房根>" --memory "<记忆根>" --sessions "<DSH_HOME>\sessions"
```

看输出里 `self` 那项的 evidence：

- `injected: true` + `hasBody: true` → **SELF 是好的**，那条红是假的
- `injected: false` → 真的没注入，去查推送插件的 `selfPath`

★ 旧版本为什么会假红：它**在历史日志里找「读不到」这几个字** ——
只要历史上出现过一次（哪怕后来修好了），就永远报红。而且它一度会**自锁死**：
报错文本本身进了日志，下一轮又读到它。

新版的判据是：**只看最后一条 `runtime-context` 快照里有没有真的装着 SELF 正文**
（认节名或正文标记 `四条硬线`），不看历史、也不看人对系统的讨论。

### 2.5 体检报「没有一个候选 node 能把 doctor 跑出输出」

**先别急着装 node —— 很可能 doctor 其实跑起来了。**

```powershell
node <kit目录>\echo\echo-doctor.mjs --json
```

**如果这条能打出 JSON**（哪怕 `overall` 是 `error`），说明 doctor 是好的，
是**体检这一层把判据写错了** —— 旧版本把「医生退出码非 0」当成「医生崩了」，
而 `echo-doctor` 的设计是**体检不通过就 exit 2**（好让 CI 能判失败）。

**已修（2026-10-24）**：判据改成「stdout 能 parse 成 JSON 就算跑起来了」，
退出码存进 `doctorExit` 当附带信息。

**所以你现在应该看到的**是真正的红因，比如：

```
══ 体检报告：error ══
【红】 配置（三个根）
  说的是：还没配好：没有配置 MEM（记忆中枢根）—— 先跑一次 agent_soul_scaffold
```

**那才是要修的东西**（本机示例是没配 `ECHO_MEMORY`），不是 node。

## 三、装上了，但某一项是空的

> **这一节是核心。** 下面每一条的症状都是「不报错，只是空的」，
> 病因都是同一个：**代码默认值假定了一台特定的机器**。

### 3.1 体检一项都不出 / 面板全灰

这几乎永远是 **子进程没起来**，而且它**不会报错**。

| 可能原因 | 判据 | 修法 |
|---|---|---|
| **`process.execPath` 不是 node** | 在 Electron 里跑时，`process.execPath` 是 `DeepSeek Harness.exe`。拿它 spawn 脚本 → 空 stdout | 设 `ECHO_NODE` 指向真正的 node.exe；新版 echo 会自动探测 |
| **找不到 `echo-doctor.mjs`** | `HUB` 拼错了目录。它和 `DSH_HOME` **没有固定关系** | 设 `ECHO_HUB` 指向 doctor 实际所在的目录；新版会先**验证文件存在**再采用 |
| **PATH 里没有 node** | 你照抄文档里的 `node xxx.mjs` 会失败 | 用绝对路径；新版输出的命令已经自动用 `process.execPath` |

**自查**：

```powershell
# doctor 到底在哪
Get-ChildItem -Path "C:\", "D:\", "E:\" -Filter "echo-doctor.mjs" -Recurse -Depth 4 -ErrorAction SilentlyContinue

# 拿这个路径试跑
& "C:\...\node.exe" "C:\...\echo-doctor.mjs" --json
```

★ **判据**：doctor 单独跑**能出 JSON**，面板却不出 → 是插件找不到它，不是 doctor 坏了。

### 3.2 换气 / 砚台 / 日记的面板是空的

**共同形状**：它们默认「账本在 `DSH_HOME/state`」，而**换气自己可能把账本落在别的地方**。

| 面板 | 它找哪 | 实际可能在哪 |
|---|---|---|
| 换气面板 | `<DSH_HOME>\state\dsh-huanqi.json` | 如果 `DSH_HOME` 为空，换气会落到**进程 cwd** 下 |
| 砚台 | 它有配置项，但旧版默认写死了作者的路径 | 用 `YANTAI_LEDGER` 指到真的账本 |
| 日记 | `RIJI_DIR` 或 cwd 下的 `diary/` | 设 `RIJI_DIR` 指到你放日记的目录 |

**第一步永远是：找到那个文件真的在哪。**

```powershell
Get-ChildItem -Path $env:USERPROFILE -Filter "dsh-huanqi.json" -Recurse -Depth 5 -ErrorAction SilentlyContinue
Get-ChildItem -Path "C:\", "D:\", "E:\" -Filter "02-墨.jsonl" -Recurse -Depth 4 -ErrorAction SilentlyContinue
```

**第二步**：用环境变量把面板指过去（每个插件的 README 里都列了它认哪些变量）。

### 3.3 面板能开，但一点就 `Failed to fetch`

**病因**：**浏览器半把后端端口写死了**（旧版写死 `19387`）。

**为什么必然失败**：DSH 的 web 端口**每次启动都可能变**
（实测过 `64895 → 65070 → 54041 → 57045 → 51971` 一路在变）。
写死一个端口的代码，在第一次重启之后就永久失效了。

**判据**：看地址栏的端口，如果它不是 `19387`，那就是这个病。

**修法**：升级插件（2026-10-23 之后所有面板都改成**同源相对路径**，让页面自己的 origin 决定）。
如果你自己改代码：把 `"http://127.0.0.1:19387"` 换成 `""`（即相对路径 `/api/...`）。

★ **一个容易误判的地方**：`new URL(req.url, 'http://127.0.0.1:19387')` 这种写法**不是**缺陷 ——
那个 base 只用来补全相对路径，**不发起连接**。别去改它。

### 3.4 拉起 ComfyUI 永远报「找不到 python」

**病因**：`model-statusbar` 的旧版**全文件没有任何 `process.env`**，路径写死成作者的机器；
而它的 README 却白纸黑字承诺了三个环境变量可配。

**修法**（新版已兑现）：

```powershell
$env:COMFYUI_DIR  = "D:\path\to\ComfyUI"
$env:COMFYUI_PY   = "D:\path\to\ComfyUI\venv\Scripts\python.exe"
$env:COMFYUI_HOST = "127.0.0.1:8188"
$env:STATUSBAR_STATE = "D:\path\to\statusbar-state.json"
```

★ **判据**：状态面板显示「未知 / 未运行」而不是「已停止」时，多半是**连不上**，不是**真的没跑**。
先确认 `COMFYUI_HOST` 的端口对得上。

### 3.5 日记界面永远是「还没有日记」

**病因**：旧版 `DIARY_DIR = RIJI_DIR || <进程 cwd>/diary`。
而用户机的 cwd 下当然没有 `diary/` → 接口返回空数组 → 界面显示「还没有」。

**修法**：

```powershell
$env:RIJI_DIR = "D:\path\to\your\diary"
```

★ 新版在目录不存在时会**明确报「请设 RIJI_DIR」**，而不是显示「还没有日记」。
**这两种提示的区别很重要** —— 前者告诉你该怎么办，后者让你以为是自己没写。

## 四、装了但行为不对

### 4.1 换气不生效 / 额度一直是满的

**先确认它到底有没有在跑**：

```powershell
# 启动探针：只要插件进了 apply() 就会写这一行
Get-Content "<DSH_HOME>\state\huanqi-boot.log" -Tail 3
```

- **有这行** → 插件在跑，问题在判据（看 `config` 段里的阈值是不是被你调太宽了）
- **没这行** → 插件没加载，看下面 4.2
- **文件本身不存在** → `DSH_HOME` 可能为空，换气把日志落到 cwd 了

### 4.2 插件「装了但没加载」

> ★ **2026-10-24 补充**：如果同时伴随 **DSH 启动即崩**，先去看
> [第二节](#二启动就崩--反复崩溃循环最急的一类)，那是另一类问题（id 撞车）。
> 本节讲的是 **DSH 起得来、只是这个插件没生效**。

DSH 里这类问题**全都是静默的** —— 不报错、不日志、界面什么都没有。按顺序查：

1. **`exports.inject` 缺写或槽位名写错** → 整包静默不加载
2. **`dsh.profile.bundles` 必须是纯字符串数组**（`["dsh-riji"]`）。
   写成 `{name:..., enabled:true}` 会被**完全静默跳过**
3. **宿主半注册的工具名撞车**（fork 别人的包时最常犯）→ 会报 `plugin tree failed to load`，
   该包路由 404，而包本身、清单、lockfile 全都对
4. **`ctx.slots.register(spec, X)` 的第二个参数必须是组件本身**，
   不能是 `function(){ return h(X) }` —— 工厂返回 vnode，槽位渲染会炸，
   而且**一个标签炸、整排顶栏一起消失**（很容易误判成「顶栏被插件弄丢了」）

★ **最硬的成功判据**：**agent 的工具列表里出现了该插件注册的工具名**。
比看界面、看日志都可靠 —— 工具名出现就说明宿主半真的加载了。

### 4.3 压缩了，但摘要看起来「没有门牌」/ 门牌打不开

**两个独立的病，别混**：

**① 摘要里没有门牌** —— 压缩发生在**隔离域**里，而门牌注入挂在**根服务域**。
判据：看 `agent-presets` 的 `isolate.compaction` 是不是 `true`。
修法：在 preset 覆盖里把 `compaction-basic` 换成带门牌的 `dsh-agent-compaction`，
pruner 换成 `dsh-agent-pruner`。

**② 有门牌但打不开** —— 曾经有个解码 bug 让**每一条门牌都不可达**
（zstd 解压时用了 `Buffer.concat` 拼 200 MB 以上的数据）。
修法：升级 `kit/echo/memindex.mjs`，然后用 `memq open <指针>` 实测一次。

★ **一定要实测**：不要因为「摘要里有 `log:session-...` 这几个字」就认为门牌能用。
**必须真的 `open` 一次，确认取回来的原文是对的。**

## 五、环境与安装形态（这一节解释「为什么改了不生效」）

### 5.1 我改了源目录，为什么不生效

同一个架构里，**三种安装形态并存**，行为完全不同：

| 形态 | 判据 | 改了源码会不会生效 |
|---|---|---|
| **junction**（目录链接） | `Get-Item <path> \| Select LinkType` 返回 `Junction` | ✓ 自动生效 |
| **硬链接** | `links` 计数 > 1，inode 与源相同 | ✓ 自动生效（改源即改目标） |
| **真实目录副本** | `LinkType` 为空 | ✗ **不生效，要重新安装/同步** |

**怎么查**：

```powershell
foreach ($p in @("dsh-yanqing-echo","dsh-yanqing-splash","dsh-yanqing-huanqi-panel")) {
  $d = "C:\Users\<你>\.dsh\profiles\desktop\node_modules\$p"
  if (Test-Path $d) {
    $i = Get-Item $d
    $f = Join-Path $d "index.js"
    "{0,-28} LinkType='{1}'  size={2}" -f $p, $i.LinkType, (Get-Item $f).Length
  }
}
```

★ **这条能解释一半的「我明明改了」** —— 先查形态，再怀疑代码。

### 5.2 `DSH_HOME` 到底有没有值

**这是最容易被忽略的一条。** 很多代码写成 `process.env.DSH_HOME || '<某个默认>'`，
而在**作者机器**上 `DSH_HOME` 永远有值 → **那个默认分支从来没被执行过**，
于是它只在**你的机器**上生效，而那里通常指向一个不存在的目录。

```powershell
# 三个作用域都看一遍
foreach ($n in @("DSH_HOME","ECHO_HUB","ECHO_SOUL","ECHO_MEMORY")) {
  "{0,-14} Process='{1}'  User='{2}'  Machine='{3}'" -f $n,
    [Environment]::GetEnvironmentVariable($n,"Process"),
    [Environment]::GetEnvironmentVariable($n,"User"),
    [Environment]::GetEnvironmentVariable($n,"Machine")
}
```

★ 如果你要验证「没配的时候会怎样」，**必须新起一个干净进程**再跑 ——
在当前 PowerShell 里 `$env:DSH_HOME=$null` 只影响这一个进程，
而很多插件是在**别的进程**里跑的（你清的那份不是它读的那份）。

node D:\path\to\dsh-agent-soul\..\verify-lossless-paths.mjs

### 6.1 照着文档抄命令，报「不认识的子命令」

**2026-10-24 起，脚本会对未知子命令报错退 2**，不再静默按默认跑。

以前是 `const cmd = argv.shift() || "stats"` —— 任何不认识的第一个参数都被吞掉，
于是 `node memindex.mjs --status` **打印一屏帮助、退出 0**，看着完全正常。
问题是 `memindex.mjs` 只支持 `build / audit / stats / verify`，
文档里的 `--status` 是过时写法。

**看到这个报错时**：

```
✗ 不认识的子命令: --status

  支持的是: build / audit / stats / verify（不写 = stats）
  ★ 如果你是从某份文档抄来的，那份文档可能过时了 —— 请把那处文档一起改掉。
```

**把那条报错连同你抄的那一行文档一起发给我们** —— 文档错比代码错更容易漏。
