四、一个 203 秒的尖峰 —— 这是最该看的一段

100 条里有一条 203 秒，把均值从 113.2 ms 直接拉到 2142.4 ms。 它不是慢查询，是一次进程冻结。
墙钟类型查询 命中位置
203,028.8 英文技术 index 2339 第 51 条 / 100

证据链（三条对得上）：

启动时 echo_stats logsState: "loading" · logs: 0 · rssMB: 348
warmup 5 次 55.9 ms / 18.1 ms / 31 ms / 26.1 ms / 42.8 ms —— 全都很快，因为日志层还没装进来，搜索不碰它
bootstrap startLogsLoad() 是 setTimeout(…, 3000) 里跑 buildLogs()，纯同步 zstd 解压
结论：3 秒延迟只是把「阻塞握手」挪成了「阻塞第 N 次查询」。 延迟到点后，buildLogs() 在主线程同步解压 7 天 / 26563 条日志， 这段时间整个进程不响应 —— 落在哪次查询头上，那次就等这么久。 这也解释了为什么实测值远超预期：7 天配置的加载峰值内存远高于 memBudgetMB: 512， 在已经有主 MCP 实例常驻的情况下会进一步触发换页。
这不是「偶发噪音」，是可复现的设计缺陷 —— 换一次查询顺序，尖峰只会落在别的词上。 设计图 §5.2 那条「分批 / worker 化」不是优化项，是这一条的正解。

六、诚实的边界

这份基线只说明「检索有多快」，不说明「检索有多准」。 100 组里没有一组验证过「返回的东西是不是真想要的那条」—— 精度要人工判定，自动化测不出来。要评精度得另起一份带标注的查询集。
还没做的： ① norm 预计算只覆盖原话层（C.words）；摘要层仍是 _n: null， 日志层与书房文本流每次重算 —— 设计图 §5.1 第 2 条只能算做了一半； ② 2-gram 倒排、分层短路（§5.2）完全没动； ③ 本轮没测 near（同义词扩展）路径 —— 那条更贵，需要单独一轮。
这组数据能当回归对照用。 下次改检索路径后重跑同一脚本、逐条对比，就能分出是真提速还是抖动 —— 噪声底线是标准差 119.5 ms（已剔除尖峰后的值）。
