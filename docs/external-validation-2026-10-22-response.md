### 不是缺陷（1 条）

**14 · SELF 模板一装就占 70.9% 预算**

数对得上：装配后的 `SELF.md` 是 **8689 字节**，对 12288 的预算 **70.7%**
（报告 v3 实测：`self.mjs：8689 B / 12288 B（70.7%）  骨架 8352 B + 活体 337 B`）。

★ 更正（报告 v3 的 N2）：我原来这里写「模板本身只有 3429 B」——**那个数是错的**。
实测 `kit/templates/SELF.src.md` 是 **8446 B**，装配后骨架 8352 B、活体只有 337 B。
也就是说**骨架才是占大头的那一块**，不是活体。

结论不变（70.7% 在设计余量内，不是缺陷），但论据换了：
真正撑起「这不是缺陷」的是**预算本来就是自由度更大的那一侧**（12288），
不是「模板很小」。原来那个数字会让人以为余量大得多。

但这不是缺陷：SELF 那条预算（12288）本来就是「自由度更大的那一侧」，七成占用仍在设计余量内。
**没改代码**，把这个数写在这里，让后来的人知道余量在哪。

### 有意留（1 条）

**15 · `scaffold` 干跑在配置不全时报 `ok=false`**

行为实测确认：干跑时 `APPLY` 为假 → 不建根目录 → `checkConfig` 因 `SOUL`/`MEM` 未配置而退出 →
**一个目录都不演示**，而干跑的意义正是演示。

但根因是干跑时 `CFG.SOUL` 是 `undefined`；要放行就得给全局配置注入占位路径，后面每一处
`path.join(CFG.SOUL, ...)` 都会拼出假路径。**改它要动全局配置层，风险与收益不匹配**（报告定级 P2）。

不是漏看，是判断：**一个 P2 的体验问题，不值得拿整个配置层去换。**

## 三、这一轮真正学到的一件事

报告里最值钱的不是任何一条具体缺陷，是它**证伪了我的验证方式**。

三条是同一个形状：

| 缺陷 | 我（或代码）拿什么当证据 | 真正要证的是什么 |
|---|---|---|
| P0-1 | `node --check` 通过 | 这个脚本**跑起来**能改到 bundles |
| P1-7 | 日志里出现 `SELF.md` 这个词 | SELF.md 的**正文**真的被注入了 |
| P0-4 | 版本号看着对 | `satisfies()` 真的返回 true |

三次都是**用一个更容易满足的条件，替代了真正要证的那件事**。
而三次的失败形态完全一样：**自检绿着，功能是坏的。**

所以本轮加的断言里，有两条不是"检查某个字符串在不在"，而是**真的把东西跑一遍**：

- `add-bundle` 那条：造一个临时 `package.json`，跑，断言 `bundles` 真的多了一项
- `semver` 那条：用真的 semver 库算，不靠肉眼看范围

自检从 **94 → 106**。
