## 实验目的

方案说「3 天会话日志 = 212 MB」，那是**按压缩比 3.2x 估的**。
先验真实成本，再改主路径。

## 实测结果（38 个文件 / 压缩态 66.9 MB）

| 项 | 方案预估 | **实测** | 差多少 |
|---|---:|---:|---|
| 文件数 | 43 | **38** | — |
| **解压后 RSS** | 212 MB | **1032.8 MB** | **×4.9 超预估** |
| **解压耗时** | — | **7783 ms** | 启动不能等 |
| 行数 | — | 35676 | — |
| 字符数 | — | **150.0 M** | — |

**★ 为什么差这么多：平均每行 4200 字符** —— 会话日志里有大量巨型工具结果（文件内容、命令输出）。

---

## 关键发现：必须截断

| 方案 | 字符数 | 估算内存 | 检索质量 |
|---|---:|---:|---|
| **存完整行** | 150.0 M | **~1033 MB** | 完整 |
| **截断到 600 字符** | **12.9 M** | **~26 MB** | **和现在完全一样** |

**★★ 截断到 600 完全无损** —— 因为 `search()` 返回的 `text` 本来就只取 `SNIP = 600`：

```js
const SNIP = 600;
push({ ...h, text: s.length > SNIP ? s.slice(0, SNIP) : s, fullLen: s.length })
```

**所以：超过 600 的部分，现在也不会返回给调用方。**

**→ 存截断版 = 26 MB，是完整版的 1/40，且检索效果不变。**

---

## 修订后的方案

| 项 | 原方案 | **修订后** |
|---|---|---|
| 常驻内容 | 完整行 | **截断到 600 的行** |
| 内存（3 天） | 212 MB | **~26 MB** |
| 启动代价 | 未估 | **7.8 秒（解压）→ 必须懒加载** |
| 768MB 预算 | 紧张 | **极其宽松（26MB）** |

**★ 内存从「要占 1GB」变成「只占 26MB」—— 你的 768MB 预算现在能装 30 天。**

---

## 解压 7.8 秒怎么办

**不能阻塞启动。三个选项：**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 懒加载** | 第一次查会话日志时才解压 | 首次慢 7.8s |
| **B. 后台预热** | 启动后异步解压，不阻塞 | T+8s 后可用 |
| **C. 只预载 1 天** | 1 天约 2-3 秒 | 快，但覆盖少 |

**★ 建议 A + B 结合**：启动后异步预热，第一次查若还没好就走「回磁盘解那一个文件」的旧路径。

## 数据结构设计（下一轮实现）

```js
// C.logs: 截断后的行，按时间倒序
{
  text: string,      // 截断到 600
  fullLen: number,   // 原始长度（判断是否被截断）
  t: string,         // 时间戳（从 JSON 里取）
  sid: string,       // 会话 ID
  seq: number,       // 行号
  ptr: string,       // 门牌 log:<sid>#seq=<n>
  _n: string,        // 预归一化（复用 norm 预计算）
}
```

★ **每个条目自带 `ptr`** —— 这样 `search()` 可以直接返回门牌，不需要额外拼。

### 一个必须记住的边界

**「三机制全部对齐」和「水位阈值」日志层都是 0 条** —— 不是 bug：

> **日志层只存每条的**前 600 字符**。关键词如果出现在长消息的后半段，就搜不到。**

这是截断换内存的必然代价（1GB → 26MB）。
**但门牌还能回原文** —— 搜不到 ≠ 拿不到，只是需要先知道有这条。

| `ECHO_LOGS_RESIDENT` | 1 | 设 `0` 完全关掉 |
| `ECHO_SESSIONS` | `$DSH_HOME/sessions` | 会话日志目录 |
