# ECHO 演进路线：检索提速 + 召回精度

> **2026-10-31 · 基于 28 号测评报告 + 本机代码实测**
> 前提：**原文路线不放**（847/847 逐字可回源是这套系统的地基，任何改动都不能动摇它）

## 零、先说结论

**你的判断是对的：现在检索机制确实不够，但不够的地方可能和你想的不一样。**

| 你的判断 | 实测核实 |
|---|---|
| 关键词命中 9-18ms | ✅ **甚至更好**（`includes` 全扫只要 66ms，命中后立刻返回） |
| 关键词不命中 → 近义 → 秒级 | ✅ **547ms 是 `norm()` 全库正则归一化**，加上书房全扫 737ms，合起来就是秒级 |
| 可以加打分/分类/权重 | ✅ **但注意：代码里已经有 `m` 字段记着匹配类型，排序却完全没用它** |
| 可以引入向量匹配 | ✅ **但它的位置不是「替换检索」，是「兜底语义路由」** |

**★ 一个必须先说清的边界**：

> **测评报告里「条级召回 0.659」，主因不是 ECHO 检索不到，是「给片段之后 agent 怎么组织答案」。**
> **ECHO 的召回准确率是 100%（847/847）—— 它交出去的每一句都是原文。**
>
> **所以：「检索提速」能治的是「慢」，「召回精度」要治的是「排序」和「覆盖」。这两件事得分开做。**

## 一、问题诊断（全部有实测数据）

### 1.1 慢在哪 —— 两个热点

| # | 热点 | 实测耗时 | 触发条件 |
|---|---|---:|---|
| **①** | **`norm()` 全库归一化** | **547.8 ms** | `near=true` 且关键词没命中时 |
| **②** | **书房全扫** | **737 ms** | `soul=auto` 且索引命中 < 5 时 |

**两个叠加 = 1.3 秒**，再加序列化，就是你感受到的「秒级」。

**实测明细**（`_bench-near.mjs`，51749 条 words）：

```
读 words.jsonl              913 ms   ← 这是启动时的一次性
① includes 全扫（命中）      66.4 ms
② includes + norm 兜底      547.2 ms   ← ②的耗时 100% 来自 norm
③ 纯 norm 51749 条          547.8 ms   （共 1672 万字符）
④ 用缓存读                  131.5 ms   （建缓存 642ms + 3MB 内存）
```

**★ 关键发现：`②` 和 `③` 几乎相等 —— 说明未命中路径的时间，全花在 `norm()` 上，跟匹配本身无关。**

### 1.2 代码根因

`kit/echo/echo-mcp.mjs:134-155`：

```js
const hitKind = (s, terms, near) => {
  if (terms.every((t) => raw.includes(t))) return "exact";   // ← 命中：短路，9-18ms
  ...
  if (near) {
    if (ns === null) ns = norm(raw);   // ← 不命中：对 51749 条全文逐条正则归一化 → 547ms
    ...
  }
};
```

**同一个函数里：命中走快路，不命中走最慢的路。**

### 1.3 排序的问题（这一条可能比「慢」更重要）

`kit/echo/echo-mcp.mjs:231-238`：

```js
hits.sort((a, b) => {
  const ra = a.layer === "L3" ? 0 : 1, rb = b.layer === "L3" ? 0 : 1;
  if (ra !== rb) return ra - rb;              // ① 一手层优先
  if (a.t && b.t) return String(b.t).localeCompare(String(a.t));  // ② 同层按时间倒序
  ...
});
```

**★★ 排序只看「层」和「时间」，完全不看「匹配得好不好」。**

**而每个命中身上其实带着匹配类型**（同文件 `:185`）：

```js
push({ ..., m: k }, r.text);   // m = "exact" | "norm" | "synonym"
```

**`m` 记了，但排序没用它。**

**后果**：搜「砚青」时，一条 `exact` 命中的原话，和一条 `synonym` 撞词命中的日志，
**排序上完全平等**（同层情况下）—— 这会直接拉低条级召回。

## 二、改进路线（三档，按「投入产出比」排）

### 🟢 A 档：不改架构，一周内能做完（收益最大）

#### A1. `norm` 结果缓存 —— 547ms → 131ms

**做法**：

```js
// loadWords 时顺手算好 norm，存进 word 对象
w.normText = norm(w.text);          // 一次性 642ms（进程启动时）
```

**代价**：启动 +642ms、常驻 +3MB 内存（相对 250MB RSS 可忽略）
**收益**：`near` 路径 **547ms → 131ms**，降 4 倍
**风险**：低。`norm` 是纯函数，缓存不会改变语义。

★ **如果嫌 642ms 启动慢**：改成**懒加载** —— 第一次查 `near` 时才建，且只建命中的那条。
但实测「只建命中的」反而更复杂（要先判断命不命中），**建议直接全建。**

#### A2. 排序加权（零成本，立刻见效）

**做法**：在排序里插入匹配质量这一档。

```js
const KIND_RANK = { exact: 0, norm: 1, synonym: 2 };
hits.sort((a, b) => {
  const ra = a.layer === "L3" ? 0 : 1, rb = b.layer === "L3" ? 0 : 1;
  if (ra !== rb) return ra - rb;
  const ka = KIND_RANK[a.m] ?? 9, kb = KIND_RANK[b.m] ?? 9;
  if (ka !== kb) return ka - kb;              // ★ 新增：匹配质量优先
  if (a.t && b.t) return String(b.t).localeCompare(String(a.t));
  ...
});
```

**代价**：**零**（`m` 字段已经在数据里了）
**收益**：排序立刻更准 —— 精确命中的排在撞词的上面
**风险**：极低。唯一变化是「同层内 exact 优先」，方向上没有争议。

★ **这是整份方案里性价比最高的一条。**

#### A3. 分层短路（治「全库扫描」）

**现在的逻辑**：墨（616）→ 摘要（1151）→ 原话（51749）→ 书房（视情况）**全扫**

**改成**：**前层够了就跳过后层**

```js
// 摘要层命中 ≥ 15 条（够回答）→ 跳过原话层的 51749 条全扫
const FAST_PATH_MIN = 15;
if (idxHits.length >= FAST_PATH_MIN) {
  // 直接走摘要结果，不扫 words
  wordsSkipped = true;
} else {
  // 才扫 words
}
```

**预估**：常见查询 **547ms → 30ms**（只扫 1151 条摘要）
**风险**：中 —— **会漏掉「只在原话里、不在摘要里」的内容**。
**所以门槛要调，且必须保留 `deep=true` 强制全扫的开关。**

★ **这条和 `soul=auto` 是同一个思路** —— 只是现在这个词略只用在书房层，没用在 words 层。

### 🟡 B 档：1-2 周，治本

#### B1. 倒排索引（inverted index）

**现在**：`terms` 逐条 `includes()` 扫 51749 条 → O(N)
**改成**：`词 → 条目 ID 列表` 的映射 → O(1) 查表

```json
// index/inv.jsonl
{"w":"砚青","ids":[12,45,78,...]}
{"w":"压缩","ids":[33,90,...]}
```

**中文要处理分词** —— 但**可以不切词，用 2-gram**：

```
"砚青亲" → ["砚青", "青亲"]     // 双字滑窗
```

**预估**：
- 查询 **< 5 ms**
- 索引体积：51749 条 × 平均 20 个 2-gram ≈ **100 万条倒排项**，约 **15-25 MB**
- 构建一次约 **2-3 分钟**

**风险**：
- **2-gram 会放大误命中**（「青亲」也会命中）→ 必须配合 A2 的排序加权
- 需要处理「索引和原话不同步」

★ **这是「近义匹配秒级」的根治方案** —— 有倒排后，`near` 只是在倒排表上多做几次查表。

#### B2. 向量召回（语义兜底）—— 只在「全都没命中」时启用

**★★ 关键定位：向量不做主检索，只做兜底。**

```
关键词命中 ≥ 1  →  用关键词结果（快、可解释、100% 原文）
关键词全不中   →  才启向量：找语义最近的 20 条摘要 → 返回它们的原文指针
```

**为什么必须这样定位**：

| 如果向量做主检索 | 如果向量只做兜底 |
|---|---|
| 结果不可解释（为什么召回这条？） | **召回理由永远是「关键词命中」，可解释** |
| 可能召回「语义相近但事实不同」的内容 | **兜底时的召回也指向原文，不生成** |
| 破坏「原文路线」的可验证性 | **原文路线毫发无损 —— 向量只负责「去哪找」，不负责「给什么」** |

**技术选型**（本机可行性）：

| 方案 | 本机可行性 | 说明 |
|---|---|---|
| **本地小模型**（bge-small / text2vec） | ✅ 可行 | ~100MB 模型，CPU 也能跑，每条约 5-10ms |
| **云 API**（OpenAI / 智谱 embedding） | ⚠️ 要网络 | 但有隐私和成本问题 |
| **不需要向量**（用同义词表扩展） | ✅ 最省 | **可能先试这个：把 `synonyms.json` 做大做细** |

★ **我的建议：先扩同义词表（零成本、立刻能做），再决定要不要上向量。**

**理由**：`near` 现在依赖 `synonyms.json`，**如果表够大够准，很多「语义查询」根本不需要向量。**

**先量一下现状**：`synonyms.json` 现在覆盖多少词？（下一步要测）

## 四、要澄清的三个边界

### ① 提速治不了「条级 0.659」

**报告自己说了**：

> **「ECHO 它只负责把记忆召回来，所以跑分多高，取决于砚青亲你（agent）对 ECHO 的运用程度。」**

**所以**：**检索再快，agent 不会组织答案，分数还是上不去。**
**提速的价值是「单位时间能查更多次」，不是「分数自动涨」。**

### ② 向量会动「原文路线」吗？

**不会 —— 只要它只做路由。**

| 向量做的事 | 是否碰原文 |
|---|---|
| 「这 20 条摘要语义最近」 | **不碰** —— 摘要本身就是索引，每条自带原文指针 |
| 返回摘要的 `ptr` | **不碰** —— 指针还是那个指针 |
| **生成答案** | ★ **这才碰，绝对不做** |

**★ 一句话：向量只回答「去哪找」，绝不回答「是什么」。**

### ③ 只追加不删要不要改？

**报告说的「会改自己」不完整，是设计选择，不是缺陷。**

**我的建议：不改。** 理由：
- 「只追加」是原文路线的地基（847/847 的来源）
- 新旧并存的问题，**可以在排序层解决**（新的权重高），不需要删旧的
- **删了就回不去了** —— 而「回不去」正是这套系统最贵的代价
