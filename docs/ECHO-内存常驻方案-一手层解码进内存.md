# ECHO 内存常驻方案 · 一手层全部解码进内存

> **2026-10-31 · 爀曦提出，砚青整理**
> 核心思路：**让「翻回去」这件事不需要碰磁盘。**

## 零、你的原话（作为这份方案的锚）

> 「我们可以把记忆、索引、检索召回服务全部缓存进内存，**记忆日志解码占用预算是 1G**，
> 其实这个思路我之前就和你提到过一次。现在之所以记忆召回是 ms 级，
> 就是得益于 ECHO 系统常驻内存，减少了冷启动的时间。
> 同义词扩展表其实也可以常驻进内存，这样也能更快。」

> 「我们把会话日志、一手层部分解码，缓存到内存，**默认常驻最近 3 天的记忆**

> 我们的回声 ECHO 系统**刚刚好缺一个设置面板**，现在只有哨兵面板，刚刚好可以设计））」

## 二、实测数据（768MB 预算的分配依据）

### 2.1 会话日志实测（`_bench-sessions.mjs`，多帧 zstd 逐帧解）

| 常驻天数 | 文件数 | 压缩态 | **解压后** | 剩余预算 |
|---|---:|---:|---:|---:|
| 1 天 | 36 | 65.4 MB | **206 MB** | 562 MB |
| **3 天（你说的默认）** | **43** | **67.2 MB** | **212 MB** | **556 MB** |
| 7 天 | 210 | 393.3 MB | **1239 MB** | **超 471 MB** ❌ |

**★ 压缩比实测：3.2x**（30169 帧/5 个样本）

**★★ 关键结论：3 天只要 212MB —— 你的 768MB 预算还剩 556MB。**

### 2.2 其他项实测

| 项 | 内存 | 备注 |
|---|---:|---|
| 索引原话解码（现在就有） | **183 MB** | 51749 条 |
| 预计算 `norm` | **+111 MB** | 让 near 从 547→131ms |
| 2-gram 倒排 | **+226 MB** | 让查询 66ms→1.9ms；建索引 20 秒 |
| 向量（摘要层 1151 条） | +1.7 MB | 兜底语义召回 |

### 2.3 768MB 怎么花（建议方案）

```
768 MB 总预算
├── 索引层（现有）        183 MB   ← 不能砍，这是地基
├── 会话日志 3 天         212 MB   ← 你的核心诉求
├── 预计算 norm          111 MB   ← 治「近义秒级」
├── 倒排索引             226 MB   ← 治「全库扫描」
├────────────────────────────────
│   小计                 732 MB   ← 余 36 MB
└── 向量（可选）           2 MB   ← 摘要层，先放进余量
```

**★ 跑完 732MB，还剩 36MB 缓冲**（JS 引擎本身有波动，留这点是保险）。

**★ 如果内存吃紧，按这个顺序砍**：

| 砍什么 | 损失 |
|---|---|
| 先砍倒排（-226MB） | 查询从 1.9ms 回到 66ms（还能用） |
| 再砍 norm（-111MB） | near 从 131ms 回到 547ms |
| **绝不砍会话日志和索引** | 那是「翻回去」的命脉 |

## 三、架构设计

### 3.1 四层常驻结构

```
┌─ L0 常驻（启动即加载，一直在内存）──────────────┐
│  ① 索引层：C.words / C.sums / C.mo / C.files     │  183 MB
│  ② 派生层：C.norm（预归一化）                     │  111 MB
│  ③ 检索层：C.inv（2-gram 倒排）                   │  226 MB
│  ④ 一手层：C.logs（最近 N 天会话日志，解码态）    │  212 MB (N=3)
└──────────────────────────────────────────────────┘
         ↑ 这四层都在一个进程里（echo-mcp 常驻）

┌─ L1 按需（查到了才解压，带 LRU）────────────────┐
│  ⑤ 超出 N 天的会话日志：查到才解压，缓存最近 8 条 │  动态
│  ⑥ 书房新文件：已有 5 秒 TTL 机制                │  已有
└──────────────────────────────────────────────────┘
```

### 3.2 关键设计决定

#### ① 会话日志的「解码态」要存什么

**不要存完整 JSON**（体积大、字段用不上）。**存「检索需要的字段」**：

```js
// 现在从日志里能拿到的（memindex 已解析过）
{
  seq: 32451,
  role: "user" | "assistant",
  text: "砚青亲，...",     // ← 检索只需要这个 + 下面两个
  t: "2026-10-31T12:00:00",
  sid: "session-15ed..."
}
```

**★ 实测：解压后 212MB 是**完整**日志。只留检索字段能压到 ~120MB。**

**但代价**：`open` 拿原文时还得回磁盘。
**判断**：**先按完整存（212MB，反正在预算内）**，除非以后要腾地方。

#### ② `norm` 什么时候算

| 方案 | 启动代价 | 内存 |
|---|---|---|
| 启动时全算 | +534ms | 111 MB |
| 懒加载（第一次查 near 时） | 0 到 +534ms | 111 MB |
| **索引构建时就算好、存进 `words.jsonl`** | **0**（读文件就有） | 111 MB |

**★ 建议第三种**：`memindex` 写 `words.jsonl` 时多写一个 `_n` 字段。
**代价**：`words.jsonl` 从 50MB 涨到 ~85MB（磁盘）。
**收益**：**启动零成本，内存里直接用。**

#### ③ 倒排索引怎么持久化

**问题**：现建要 **20 秒**。

**方案**：**建一次，存成二进制文件，启动时直接读。**

```js
// index/inv.bin（自定格式）
// [gramCount][gram1_len][gram1][ids_count][id1][id2]...
// 用 Int32Array 存 ids —— 比 JS 数组省 4-5 倍内存
```

**预估**：
- 文件体积：**~60 MB**（比 JS 数组的 226MB 小很多）
- 加载：**~1.5 秒**（读 + TypedArray 构造）
- 内存：**~80 MB**（用 Int32Array 而不是普通数组）

**★ 这一条能把「226MB + 20 秒」压到「80MB + 1.5 秒」。**

**但要做实验验证**（见 §5 待办）。

## 四、设置面板设计（你说 ECHO 缺一个）

### 4.1 现状

| 面板 | 状态 |
|---|---|
| 哨兵面板 | ✅ 有（`dsh-yanqing-*` 系列里的某个） |
| **ECHO 面板** | ❌ **没有** |

### 4.2 面板要放什么

**分三组：**

#### A. 内存与常驻（核心）

| 项 | 控件 | 默认 | 范围 |
|---|---|---|---|
| **记忆常驻天数** | 数字输入 / 滑块 | **3 天** | 1–7（超 7 天要警告） |
| **内存预算** | 数字输入（MB） | **768** | 256–2048 |
| **当前占用** | 只读显示（实时） | — | 分项：索引/日志/norm/倒排 |
| **超预算时怎么办** | 下拉 | **先砍倒排** | 砍倒排 / 砍 norm / 砍日志天数 / 只警告 |

#### B. 检索行为

| 项 | 控件 | 默认 |
|---|---|---|
| `soul=auto` 触发线（索引命中 < N 才扫书房） | 数字 | 5 |
| 书房扫描 TTL（秒） | 数字 | 5 |
| `near` 默认开关 | 开关 | 关 |
| **分层短路阈值**（摘要命中 ≥ N 就跳原话层） | 数字 | 15 |
| 排序权重（匹配质量 vs 时间） | 滑块 | 匹配质量优先 |

#### C. 索引维护

| 项 | 控件 | 说明 |
|---|---|---|
| 索引状态 | 只读 | 条目数 / 最后构建时间 / 文件数 |
| **重建索引** | 按钮 | 带确认（会跑几分钟） |
| **重建倒排** | 按钮 | 带确认（20 秒） |
| 上次重建耗时 | 只读 | 用于判断要不要重建 |

### 4.3 面板不能做什么（边界）

| 不能 | 为什么 |
|---|---|
| **不能改「原文路线」** | 那是铁律，不是配置 |
| **不能删记忆** | 只追加是地基 |
| **不能改指针格式** | 改了所有历史指针全废 |

## 六、风险与边界（必须写清）

### ① 内存预算的「硬」在哪里

**JS 没有真正的内存上限** —— 768MB 是**我们自己定的纪律**，不是引擎强制的。

**判据**：
- 超过预算 **80%** → 面板亮黄
- 超过预算 **100%** → **按预设策略砍**（先砍倒排），并记一条日志
- **绝不静默 OOM**

### ② 常驻天数不等于「只能查这么多天」

**★★ 重要**：常驻 3 天 ≠ 只能查 3 天。

| 场景 | 行为 |
|---|---|
| 查最近 3 天 | **内存直读，ms 级** |
| 查 3 天以前 | **回磁盘解压那一份**（慢，但能查到） |

**这就是为什么「只追加」不能改 —— 磁盘上的原文永远都在。**

### ③ 启动时间会变长

| 项 | 现在 | 加常驻后（估） |
|---|---:|---:|
| 读索引 | 913 ms | 913 ms |
| 读会话日志 3 天 | 0 | **~1.5-3 s**（解压 43 个文件） |
| 读倒排 | 0 | ~1.5 s |
| **合计** | **~1 s** | **~4-6 s** |

**★ 这是「冷启动慢一次，换之后每次都 ms」的取舍 —— 和现在 ECHO 的哲学一致。**

**缓解**：**懒加载**（第一次查才加载），或者**后台预热**（启动后异步补）。

### ④ 数据一致性

**会话日志会变（新会话在写）**。

**判据**：**按文件 mtime + size 判断是否重载**（和 `C.words` 的 `statKey` 同款机制）。

**不用整个重扫** —— 只扫「mtime 变了的那几个」。
