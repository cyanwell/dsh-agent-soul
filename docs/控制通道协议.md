# 控制通道协议（v1）

> **这是 agent-soul 的第二条腿。**
> 第一条是 MCP（宿主调它）；这一条是**它调宿主**。
> 2026-11-07 定版，实测 10 项全绿（`tools/control-selftest.mjs`）。

---

## 为什么需要这条腿

MCP 是**被调用**的 —— v4 只能等宿主来问。
但爀曦的原话是「**触发源是 v4 触发 harness，不是反过来**」。

没有这条通道，那句话就是空的：**灵魂不能主动说「该动了」。**

---

## 核心设计：v4 认识「能力」，不认识「宿主」

```
        agent-soul（常驻）
   ┌──────────────────────────────┐
   │  ① MCP server   宿主调它（已有）   │
   │  ② 控制通道 WS   它推给宿主（本条）│
   └──────────┬───────────────────┘
              │  宿主连上来，自报会什么
              ▼
   { host:"dsh", caps:["followup","huanqi","pruner"] }
              │  v4：「该换气了」
              ▼
       广播给所有会 huanqi 的宿主
```

★ **v4 的主程序里一次都不该出现 `'dsh'` 这个词。**
换宿主 = 新写一个适配器连上来、自报能力。**v4 一行不改。**

**★ 2026-11-07 实测过这句不是口号：**

| 项 | 结果 |
|---|---|
| 扫 `src/` 代码里的 `dsh` | 13 处，**全在适配器（`migrate/dsh.mjs`）和一处命名/日志里** |
| 真起一个假宿主 | v4 认了它（`host=fake-codex`），和 dsh 并列 |
| 派活给它 | 它收到 `exec`、回了 `ok:true`，**v4 一行没改** |

★★ **但这一条有个更深的教训**：在这之前，`hub.exec()` 写着却 **没有任何调用者** ——
通道能连、能握手、能被 `/api/control` 看见，**v4 从来没派过活**。
**「能连」和「能推」是两件事。** 只看 `connected=2` 就说「解耦成立」，是拿「连上了」冒充「能干活」。

## 消息（全部是 JSON 短文本帧）

### ① 宿主 → v4：hello（连上后**第一件事**）

```json
{
  "type": "hello",
  "host": "dsh",
  "caps": ["followup", "huanqi", "pruner"],
  "meta": { "pid": 1234 }
}
```

**`caps` 是这个协议的全部。** 你报什么，v4 就当你做什么。
不报的能力，v4 永远不会发给你。

### ② v4 → 宿主：welcome

```json
{ "type": "welcome", "id": "host-1-mw5u4imj", "you": "dsh", "caps": ["followup"] }
```

★ 收到 welcome 才算真连上。**别在收到之前就认为成功了。**

### ③ v4 → 宿主：exec（推指令）

```json
{ "type": "exec", "id": "cmd-5", "cap": "huanqi", "action": "break-turn", "args": { "streak": 2 } }
```

### ④ 宿主 → v4：result（**必须回**）

```json
{ "type": "result", "id": "cmd-5", "ok": true, "data": { } }
{ "type": "result", "id": "cmd-5", "ok": false, "error": "做不到的原因" }
```

★★ **不回 = v4 那边 15 秒后超时 reject。**
而「做不到」**必须用 `ok:false` 回**，不许静默 —— 静默和「卡住」在 v4 眼里是一样的。

### ⑤ 宿主 → v4：state（可选，但强烈建议）

```json
{
  "type": "state",
  "contextTokens": 482000,
  "contextWindow": 1048576,
  "turnId": "turn-7",
  "outputTokens": 12
}
```

★ **这就是「检测宿主上下文污染」的数据源。**
v4 在外面看宿主，反而看得见宿主自己看不见的东西（上下文塞满、输出预算烧光、反复绕圈）。

## 能力清单（v1）

| cap | action | args | 谁能做 | v4 怎么派 |
|---|---|---|---|---|
| `followup` | `say` | `{text}` | **任何宿主**（触发一轮） | `soul_ask_host` |
| `huanqi` | `break-turn` | `{streak}` | ⚠️ **只有宿主内部能做** —— 要截断当前回合 | `soul_ask_host` |
| `pruner` | `prune` | `{keep, drop}` | ⚠️ 同上 —— 要改 tool result | `soul_ask_host` |
| `state` | `report` | 见 ⑤ | **任何宿主**（只上报，不收指令） | 不收指令，宿主自己发 |

### ★ 一个必须说清的边界

**v4 负责「判断」，宿主负责「执行」。**

| 能力 | v4 能给什么 | v4 给不了什么 |
|---|---|---|
| followup | 「该说话了」+ 说什么 | —— |
| huanqi | 阈值、重试几次、什么时候该截断 | **「怎么截断」永远只能在宿主里发生** |
| pruner | 留什么、裁什么 | **「怎么裁」同上** |

这不是设计缺陷，是**原理边界** —— 和「MCP 不能往宿主界面画画」是同一类。

## v4 怎么派活：`soul_ask_host`

**这条通道有三个使用者，从下往上：**

| 谁 | 怎么用 | 什么时候 |
|---|---|---|
| 宿主（DSH 等） | 调 MCP 工具 `soul_ask_host` | 人让它做 |
| v4 的自主器官 | 判断出「该动了」→ 内部调 `control.exec` | 静默超阈值 |
| 脚本 / 测试 | 同 ①，或直接 `control.exec` | 回归、排查 |

### 参数是 `cap`，不是 `host`

```json
{
  "cap": "followup",
  "action": "say",
  "args": { "text": "该动了" },
  "host": "（可选）dsh",
  "timeoutMs": 15000
}
```

★ **为什么第一个参数是能力而不是宿主的名字** —— 因为 **v4 不认识宿主**。
它认识的是「有谁能干这件事」。名字只是调试用的。

### 自动挑宿主的规则（三条，可解释）

| 情况 | 怎么挑 | 为什么 |
|---|---|---|
| 只有一个能干 | 就它 | —— |
| 多个能干 | 挑 **state 最鲜** 的那个 | 有新鲜的 state 说明它活着。连上来却从不说话的宿主，能派活不代表会干活 |
| 都没上报过 state | 按连接顺序，**并在返回里说清这是退让** | 不知道就看运气，但**不许装作知道** |

### 会跳过「桩」

宿主在 hello 的 `meta.stubs` 里声明过「能力在、路没通」的 cap，**不会被派过去**。
理由：派了只会等超时。**提前一秒知道** 和 **十五秒后超时** 是两件事。

### 返回里一定有 `why`

```json
{ "ok": true, "host": "host-2-…", "hostName": "dsh", "cap": "followup", "why": "只有它在干 followup", "data": { "delivered": true } }
```

★ **不许只回 `host-2-mw5u4imj` 这种 id** —— 人看不懂，而且下次重启就变了。

## 写一个适配器（三步）

以 DSH 为例（`dsh-agent-soul-bridge`）：

```js
// 1. 连上，自报能力
ws.send({ type:'hello', host:'dsh', caps:['followup','huanqi','pruner'] });

// 2. 收指令，按 cap 分发，必须回执
ws.onmessage = (m) => {
  const msg = JSON.parse(m);
  if (msg.type === 'exec') {
    if (msg.cap === 'followup') {
      agent.followup(msg.args.text);
      ws.send({ type:'result', id:msg.id, ok:true, data:{} });
    } else {
      ws.send({ type:'result', id:msg.id, ok:false, error:'未实现' });  // ★ 留桩也要回
    }
  }
};

// 3. 每轮上报状态
ws.send({ type:'state', contextTokens, contextWindow, turnId, outputTokens });
```

★ **断线要自己重连**（指数退避 1s→2s→4s→…→30s 封顶）。
★ **零第三方依赖** —— v4 那边是手写的 WS（`src/control/ws.mjs`，150 行），你也不用引库。

## 自检

```bash
node tools/control-selftest.mjs        # 14 项：协议层（握手/帧/重连/断开清理）
node tools/control-live-selftest.mjs   #  5 项：真链路（起假宿主 → v4 认它 → 派活 → 回执）
```

★ **两个测的不是同一件事**：

| 套件 | 测什么 | 会不会起进程 |
|---|---|---|
| `control-selftest` | 协议层：握手正确吗、帧编解码对吗、掉线清理干净吗 | 不起，纯内存 |
| `control-live-selftest` | 端到端：v4 **真的**把活派给了一个它从没见过的宿主吗 | 起一个假宿主 |

★★ **第二个是解耦的回归门。** 动协议之前先跑它 —— 它挂了就说明「换宿主不用改 v4」这条破了。

## 两个今晚踩到的坑（写给后来者）

### ① 只监听 `close` 不够 —— 掉线时先到的是 `end`

```js
socket.on('end', () => this.#closed());    // ★ 必须有
socket.on('close', () => this.#closed());
socket.on('error', () => this.#closed());
```

实测：客户端 `destroy()` 之后，服务端 **`'end'` 立刻来，`'close'` 600ms 都没来**。
只监听 close 的后果是 **注册表里永远留着死连接**，而 `whoHas()` 还把它当活的。

### ② 宿主不回声要能超时，不能永远挂着

`hub.exec()` 有 15 秒默认超时。**这一条是为了让「宿主卡住」变成「一个错误」，而不是「一个悬案」。**
