# 创造 · 造东西的总入口

**这不是一套新能力，是一张目录。** 它只做两件事：告诉你「这件事该用哪份工艺文档」，以及「动手前必须先确认什么」。

## 一、先分流：你要造的是哪一种

| 你要造的 | 读这份 | 它的核心约束 |
|---|---|---|
| **DSH 插件**（有 UI / 有工具 / 要进驻主程序） | `cordis-plugin-development` | 先查 Inspect Provider 拿真实接口，**不许从服务名推断 API** |
| **agent preset**（一份 composition，决定一个会话有什么） | `editing-cordis-compositions` | 先确认这行属于 host 还是单个会话，**不许猜**
| **skill**（一份按需加载的说明书） | `huashu-nuwa`（造新视角）或直接照 `SKILL.md` 格式手写 | description 里必须写清**什么时候触发**，否则它永远不被读到 |
| **一个「视角」**（把某人的思维方式做成可调用的 skill） | `huashu-nuwa` | 证据优先：每条判断都要能指回一手材料 |

★ **分不清的时候，问一句**：这个东西是「让 agent 能做以前做不到的事」（→ 插件 / preset），还是「让 agent 知道以前不知道的事」（→ skill / 视角）？

## 二、动手前的共同检查（三种都适用）

**1. 它真的需要被造吗？**
先搜一遍现成的：`skills/` 目录、插件市场、已有 preset。
**收编优于重建** —— 如果三份文档合起来已经覆盖了，那就写一份索引，不要再造第四份。

**2. 验收标准必须在开工前写下。**
后补的标准会自动迁就结果，那是事后追认。
- 插件：工具列表里出现该工具名 = 宿主真加载
- preset：挂上之后 `skills/` 真的被解析到（不是配了个指向空目录的引用）
- skill：一个新会话在**不点名**的情况下，遇到对应场景会不会主动 read 它

**3. 它归谁复制？**
★ **这是最容易漏的一条**：写在 preset 目录里的东西**随 preset 走**，写在用户技能根里的**随人走**。
选错了，换一台机器就失效。

## 三、一条来自本机的教训

★ **「配了引用」不等于「目录存在」。**
2026-11-03 发现 `preset-soul-all.yml` 里 `customSkillDirs` 早已指向 `skills/`，
但仓库里那个目录根本不存在 —— 部署端有，仓库端没推。
**判据：任何 `customSkillDirs` / `baseUrl` 引用，都要去仓库里 `ls` 一次。**
