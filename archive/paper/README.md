## 为什么它在这个仓库里

这个仓库的 [`soul/`](../soul) 是**说明书**：你要做自己的灵魂，该知道什么。
而这一篇是**它的依据**：为什么这么设计，以及这么设计之后**实测跑成了什么样**。

```
这一篇              →  为什么这么设计（判断 · 机制 · 实测 · 局限）
soul/               →  该知道什么（说明书）
dsh-agent-soul      →  零件（本仓库 plugins/）
```

**★ 那三条判断（摘要只能是索引 / 损失的是线索 / 瓶颈在触发）最早是在这里被写下来的** ——
`soul/` 里那几条是它们的复述。

## 它有什么别的文章没有的

市面上讲 agent 记忆的文章很多，**但很少有一篇是这样的**：

```
· 有失效链 —— 不是「这样做更好」，是「不这样做会怎么坏」
· 有实测 —— 一段时间连续运行的真实规模数据
· 有对照 —— 同一模型、同一使用者的两期对比
· 有局限 —— 专门一节讲「本文没证明什么」
```

★ **最后一条最难得**：一篇讲自己系统的文章，愿意把**它没测什么**写清楚。
那和 `dsh-agent-mnemon-probe` 那条纪律是同一个东西 ——
**一个测量工具最值钱的部分，是它说得出自己测不到什么。**

## 读法建议

**它不是教程，是一篇论文。** 如果你时间有限，按这个顺序读：

```
1. 问题定义        —— 它到底在解决什么（不看这节，后面都是空的）
5. 三项设计判断    —— 全文最值钱的一节，不到一页
6. 核心机制        —— 五条，每条都连着上面某一条判断
11. 本工作的价值   —— 六条，看它想留下什么
```

**中间那几节（相关工作、实验设计）可以跳。**
**★ 但如果你要自己搭一套，别跳 §9「局限与未来工作」。**

---

## 关于文中数据

**它是某个真实实例的实测值**（会话数、日志体积、运行周期、主导更替次数）。
那些数字的作用不是「性能指标」，而是**「这件事真的跑过」的证据**。

★ 换句话说：**你不需要复现那些数字，你需要的是那些数字背后被验证过的机制。**
