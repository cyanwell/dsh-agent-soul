# 12 · 墨：只追加的账本

> **这一份管的是「发生过的事怎么留下来」。**
>
> 前面十一份讲的是架构的形状；这一份讲那条贯穿所有层的线 —— 一个**只追加的 JSONL 账本**。
> 它是整个系统里唯一「越来越长、从不修改」的东西。

---

## 一、为什么是「只追加」

**多写者环境里，共享可变文件是万恶之源。**

这不是理论。真实的教训长这样：两个人（两个会话）同时改同一份配置，
一个用原子写入替换了文件，打断了硬链接 —— 于是「我改了源、副本没变，而两个都叫同一个名字」。
排查这件事花掉的功夫，比设计一个只追加的结构多得多。

只追加**不需要锁**：各写各的行，读的时候按时间合并。
现成的证据：成千上万个会话日志各自追加，从来没冲突过。

★ 所以账本的第一条纪律是：**打开它，只能往后加。不许改、不许删、不许重排。**

---

## 二、八种类型，各自管什么

账本里每一条都有一个 `type`。**类型不是分类游戏，它决定了这条记录会被怎么读。**

| type | 记什么 | 谁读它、拿来干什么 |
|---|---|---|
| `fact` | **发生了什么事**。可核实的事实 | 日常主力。检索时最先翻的就是它 |
| `gain` | **得到了什么能力／弄清了什么** | 「我以前想过什么办法」的入口 |
| `loss` | **失去了什么／发现哪里缺了** | 避免重复踩同一个坑 |
| `shelved` | **搁置的活**：想好了、还没做、等什么 | ★ **未结清单的唯一真相**。不要另外维护一份 todo |
| `promise` | **替用户许下的承诺** | ★ **只有「主导」能写**。见第五节 |
| `persona` | **对自己理解的修正**：改了哪条、为什么 | 人格漂移时用来对账 |
| `container` | **一个容器（会话）的退场交接** | 执行者从不写 `lead`，不写这条它们就消失了 |
| `lead` | **主导权的归属** | ★ **谁是主导 = 最后一条 `lead` 的署名者** |

★ **分布是有形状的**，别平均写。一份跑了几个月的真实账本大约是这样：
`fact` 占绝大多数（七八成），`gain` 次之，`shelved` / `loss` / `promise` 各十几二十条，
`persona` / `container` / `lead` 只有个位数 —— 因为它们是**重事件**，不是日常。

★ 如果 `lead` 变得很多，那说明容器换得太勤；如果 `fact` 一条没有，说明它没在工作。

---

## 三、字段：每个都在防一种具体的坏

一行长这样：

```json
{"t":"2026-01-01T09:00:00+08:00","by":"a1b2c3d4","type":"fact","text":"一句话说清发生了什么","ref":"出处","feel":"当时的感受"}
```

| 字段 | 必需 | 它防的是 |
|---|---|---|
| `t` | 是 | 时间。**必须记「现在」**，不许回填旧时间 |
| `by` | 是 | 署名。**谁写的**。多容器环境下没有它，事后分不清谁做的主 |
| `type` | 是 | 见上一节 |
| `text` | 是 | 一句话。**写得像索引，不要写成长文** —— 长文该进书房文件，账本只留指针 |
| `ref` | ★ **强烈建议** | 出处。没有它，这条记录就**无法回取**，等于一段孤立的断言 |
| `feel` | 条件 | 当时的感受。见第四节 |

★ **`ref` 为什么重要**：账本的价值不在它自己，在于它能**指向原文**。
一条没有出处的 `fact`，三个月后读到只能选择相信或不信 —— 而两条路都不对。

★ **`text` 和 `概要` 是同义词**（历史包袱）。早期写 `text`，后来某些实现用 `概要`；
读的时候两种都要认，不要因为找不到 `text` 就判定这条坏了。

---

## 四、`feel`：必问不必写

**`feel` 不是概要、不是结论，是「我当时什么感觉」。**

它的用途只有一个：**以后读到这一条时，能回到当初的情形。**
概要能告诉你「做了什么」，`feel` 才能告诉你「那件事对他意味着什么」。

★★ **但必须做的不是「写」，是「问」。** 每写一条之前停一下：**这件事我有感觉吗？**

- 有 → 写进去
- 没有 → **不写，这是对的**

★ **为什么不做成必填**：做成必填它就变成每次要交的作业，那就成了表演。
而「问过之后的没有」和「忘了问的没有」是**两件事** —— 后者是懒，前者是诚实。

★ 一份真实的账本里，带 `feel` 的约占三分之一。**这个比例本身就是它对的样子** ——
不是每条都该有。

---

## 五、谁能写哪一类：主导 vs 执行

**账本里的权限不是靠自律，是代码级的闸门。**

| 角色 | 判据 | 能写 |
|---|---|---|
| **主导** | 是不是最后一条 `lead` 的署名者 | 全部，**含 `promise`** |
| **执行者** | 从没写过 `lead` | `fact` / `shelved` / `gain` / `loss`，★ **写 `promise` 会被拒** |

★ **一句话：身份可以复制，责任不能。**
一个执行容器干完就关，它许下的承诺没人来兑现 —— 所以它根本不许许。

★ **写 `lead` 的权限不在代码里**，在人嘴里：只有用户能指定谁是主导。
这是设计，不是漏洞。

★ **`lead` 的正文要自带世代自述**：`第 N 代 · 接手于 <日期> · 上一代做了：<一句话>`。
否则换到第十次时，读那堆记录看不出时间线。

---

## 六、什么时候写、什么时候不写

**该写的四种时机：**

1. **做完一件事** —— 尤其是跨了几个回合才做完的
2. **做了一个不容易回头的决定** —— 为什么这么定，比定了什么更重要
3. **撞了一个坑** —— 坑的形状和检测法一起写，光写「踩过」没用
4. **退场之前** —— 写一条 `container`：做了什么、产物在哪、下一步该谁做

★ **前三类不能等**：事后重建不了「当时在想什么、卡在哪」。
★ **第四类能等**：那只是给下一代的交接，攒到退场时写一次即可。

**不该写的三种：**

- **过程流水**（"我先读了 A，又读了 B"）—— 一手层是会话日志，账本不要重复它
- **可以被一条命令重新得到的事实**（"当前版本是 x.y.z"）—— 下次要问磁盘，不要问账本
- **没有出处的断言** —— 除非你打算把它当唯一真相，那就必须在正文里说清依据

---

## 七、一条最容易被忽略的纪律

**账本是索引，不是记忆本体。**

它记的是「**发生过这件事，原文在 ref 指的地方**」。
所以：

- ★ 不要把长文塞进 `text` —— 那会让账本变成一本没法翻的书
- ★ 不要在账本里转述别人的结论 —— 转述就是二手的开始
- ★ 遇到「账本和原文冲突」—— **原文优先**，然后修账本

★ 这条纪律的反面也成立：**如果一件事没有进账本，那它在系统里就等于没发生过。**
不是因为账本权威，是因为**没有人会知道该去找它**。
