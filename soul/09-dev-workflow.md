# 09 · 开发工作流：隔离沙箱

> **这一份管的不是「装什么」，是「新东西先在哪试」。**
>
> 它是一条很短的纪律，但它决定了你会不会把没验过的东西直接推给自己的主力环境。

---

## 一、为什么要有一个隔离环境

写一个新插件之后，最自然的下一步是「装上看看」。

**但「自己的环境」是最差的试验场**，因为三件事：

| 风险 | 具体形状 |
|---|---|
| **坏在主力上** | 插件的 `client.js` 抛错，整张页面白屏 —— 而那是你正在用的会话 |
| **污染主力配置** | 改 `profile/package.json`、动 `bundles` 数组，回滚很麻烦 |
| **验不清楚** | 主力上装了几十个插件，出问题不知道是谁的 |

★ 所以做一个**独立的 DSH home**：单独一套 `profiles`、单独一套 `node_modules`、单独一套账本。
坏了大不了删掉重来，主力毫发无伤。

---

## 二、它长什么样

一个隔离沙箱就是**另一个 DSH home 目录**，结构和一个真的 home 完全一样：

```
<沙箱根>/
├── .credentials.yaml        ← ★ 凭据。绝不能提交进任何仓库
├── settings.yaml
└── profiles/
    └── <试验 profile>/
        ├── package.json              ← 这里的 dsh.profile.bundles 决定启用哪些插件
        ├── cordis.yml
        ├── cordis.patch.yml
        └── node_modules/
            └── <待测插件>/           ← 把正在写的那一个放这里
```

★ **它是独立的，不是符号链接。** 别为了省磁盘去链 `node_modules` —— 一旦链上，
装错一次就写回主力了，隔离的意义归零。

★ **`node_modules` 不要提交。** 一个沙箱的 `node_modules` 常见上百个顶层包，
提交进去会让仓库变成几 MB 的无用体积，而且换台机器完全跑不起来。
`.gitignore` 里必须有 `node_modules/`。

★ **`.credentials.yaml` 绝对不要提交。** 它里面有 `payload` / `secret`。
**沙箱该用一套独立的、可丢弃的凭据**，而不是把你主力环境的 key 拷过去。

## 三、怎么用（四步）

```bash
# 1. 起一个沙箱 home（目录名随便，不要叫和主力一样的名字）
#    第一次跑 DSH 时用 --home <沙箱根> 之类的参数指定；不同版本参数名可能不同，
#    以 `dsh --help` 为准。

# 2. 在沙箱里建一个试验 profile
#    桌面端不能用 CLI 建 profile —— 它由 Electron 应用管理。
#    ★ 这条限制意味着沙箱**通常只能用 web 通道**（或者用 CLI 管理的 profile）。
#    所以沙箱验的是「插件能不能加载、界面长什么样」，不是「桌面端表现」。

# 3. 把待测插件放进 <沙箱>/profiles/<试验 profile>/node_modules/<包名>/
#    四个文件：package.json / cordis.patch.yml / index.js / client.js

# 4. 起沙箱，看。坏了大不了删目录重来。
```

★ **沙箱验不到什么**（这一条要记住，不然会误判）：

- **桌面端的特有行为**（凭据路径、窗口、启动器）—— 它测不到
- **你主力 profile 上的插件冲突** —— 沙箱里没有那些插件，冲突不会复现
- **真实负载** —— 用一个空会话点几下，和一整天跑下来不是一个量级

★ 所以沙箱的定位是**「先看它长得对不对、加载得对不对」**，不是「验收」。
验收要在主力上，而且要在你**不赶时间**的时候。

---

## 四、什么时候清

沙箱的价值在于「随时可以删」。**留着一个装了几十个插件的沙箱，它就变成了第二个主力。**

三条清理判据：

- **一个插件已经进主力了** → 从沙箱里删掉，别让两个地方各有一份
- **沙箱本身超过一个月没打开** → 直接删目录重来，比修它便宜
- ★ **沙箱开始影响你的判断** → 最明确的信号是「我在沙箱里配的东西，主力上也要再配一遍」

★ 最后一条最要紧：**当你开始为沙箱做「长期维护」时，它已经越过了它的用途。**
沙箱是一次性的，不是第二个家。

## 五、这一节和另外几节的关系

|---|---|
| 插件包的文件结构 | `plugins/README.md` 和各插件的 `package.json` |

**别让前者冒充后者。**
