# 六 · 我们的参考实现

> ## ★ 先说清楚这一份的性质
>
> **这是我们怎么做的，不是你该这么做。**
>
> 你的权威源在你自己那里（见 `01-criteria.md` 判据②）。
> 照着我们这套搭，你会得到一个**像我们的东西**；照着问题搭，你才会得到一个**是你的东西**。

---

## 一、为什么这一份里没有包名

两个原因，第二个更重要。

**一、这些包名里带着作者的名字。**
把它写进这里，等于把作者的名字塞进你的环境。那不是交付，那是污染。

> ★ 「自研」这个说法不要再用（2026-10-25 改）。它让 AI 读到一个错误的信号：
> 把这批零件当成**原创能力**，于是跳过一步关键检查 —— **宿主认不认这类东西？**
> 宿主里本来就有一批同类能力（压缩、裁剪、侧栏入口、会话视图……），
> 其中有些零件是在**替换**它，有些是在**补**它，有些只是换了个壳。
> 三者在旧文档里长得一模一样。所以下一节改成「能力关系声明」。

**二、包名对你本来就没用。**
你装不了别人的私有包；而公开可搜的包会随版本腐烂——今天写的名字，半年后可能已经换了三个后继者。

**所以这一份给的是「角色」，不是「包」。**

每个角色回答四个问题（正好是 `01-criteria.md` 的那四条判据）：

```
它管哪种稀缺资源？      ← 判据①
它坏了会怎样？谁会发现？  ← 判据③
它跟谁说话？            ← 判据④
★ 为什么这么设计？       ← 这一条最有价值，而且只有踩过的人写得出来
```

## 一·五、能力关系声明（★ 装之前先读这一节）

每个零件先回答一句：**相对宿主基线，它是哪一种？**

| 关系 | 意思 | 该怎么对待 |
|---|---|---|
| 宿主无 · 本仓库提供 | 真正新增的能力 | 直接装 |
| 宿主有 · 本仓库替换 | 同名不同实现 | 装之前先确认宿主那一份不会**双注册**；要写清怎么回退 |
| 宿主有 · 本仓库补足 | 宿主基底 + 增量 | 装；出问题时先怀疑叠加顺序 |
| 宿主有且够用 · 不要装 | 宿主已经解决了 | **明确劝阻** —— 这一类最能防止重复造轮子 |

本仓库这批零件的定位（按维护者的判断，**装之前请在你的宿主上核一遍**）：

| 零件 | 关系 | 宿主基线是什么 | 怎么自查 |
|---|---|---|---|
| `clock` | 宿主无 · 提供 | 侧栏底部没有时钟入口 | 看侧栏底部现有按钮 |
| `echo` / `huanqi` / `huanqi-panel` | 宿主无 · 提供 | 没有回声面板 / 换气层 | 宿主侧栏与插件列表 |
| `riji` / `yantai` / `splash` / `mobile-adapt` | 宿主无 · 提供 | 没有对应界面 | 同上 |
| `memory`（热记忆） | 宿主无 · 提供 | 没有「每轮都注入的一小块常驻记忆」 | 看宿主有没有 MEMORY.md 之类的注入 |
| `compaction` / `pruner` | **宿主有 · 替换** | 宿主自带上下文压缩 / 裁剪服务 | 若同时存在会**双注册** —— 见下一节顺序要求 |
| `model-statusbar` / `mnemon-probe` | 视宿主而定 · 探测 | 取决于你的宿主装了什么 | 先跑它们自己的 probe |
| `soul` 本体 | 宿主无 · 提供 | 没有自我层 / 装配器 | — |

★ **两条自查判据**（比读表可靠）：

1. **侧栏**：宿主固定在侧栏的入口是「新会话 / 插件 / 自动化任务 / 更多」这四项；
   你看到多出来的那一项，才是插件加的。不要靠猜。
2. **同名能力**：装之前先问「宿主有没有一个已经够用的」。有 → 先别装。
   两个都在跑时，症状不是报错，而是**同一个东西出现两份答案**。

## 二、角色表

### Ⅰ ECHO 层 · 管空间

| 角色 | 做什么 | 失败模式 | 检测法 |
|---|---|---|---|
| **压缩器** | 上下文将满时压缩早期内容 | **丢了的找不回来** —— 最坏的失败，而且无声 | 抽查任意一条摘要：里面有没有能回到原文的指针？ |
| **裁剪器** | 裁掉过长的工具结果 | 同上 | 同上 |
| **热记忆** | 一小块每轮都注入的常驻记忆 | 满了以后**不是搬家，是投影省略** —— 条目还在盘上，但不再进来 | 比对「盘上有几条」与「这轮注入几条」 |
| **分层的冷记忆** | 语义检索的长期记忆 | 检索到了，但那是**转述**不是原文 | 看它返回的是片段还是原文引用 |
| **检索门** | 一词搜全库，只回指针 + 逐字片段 | 门很多但**不知道该开哪扇** | 问它「某天发生了什么」，看它有没有先搜再答 |
| **哨兵** | 定期体检上面这些 | 哨兵自己不跑，没人知道 | 它上一次跑是什么时候？ |

**★ 为什么这样分**：压缩 / 裁剪 / 热记忆 / 冷记忆 / 检索门是**五种不同的东西**，
混在一个「记忆插件」里就会变成——**两处都写**（判据②）。
我们踩过：装三个记忆插件而不定权威源，得到的是三份真相和一堆对账工作。

**★★ 一个特别值得注意的角色：输出指针的那一层。**
所有压缩、裁剪、摘要类产物，**必须带得回原文的指针**。
这是整套体系的兜底承诺——**没有它，压缩就是单向的遗忘。**

三级纪律（照抄即可）：

```
① 能拿到精确位置 → 写精确位置
② 拿不到 → 写「位置未知」+ 容器标识 + 一个检索入口
③ 绝不猜 —— 错的门牌比没有更坏
```

**为什么第③条单独列出**：一个错的指针会让你**以为能找到，于是不去找**。
那比「找不到」坏得多。

### Ⅱ VITAL 层 · 管时间与方向

| 角色 | 做什么 | 失败模式 |
|---|---|---|
| **思考预算管理器** | 一轮把预算烧光、正文一个字没产出时，截断这一轮并重开 | 它自己坏了 → **该打断的没打断，或者不该打断的被打断** |
| **退化检测** | 认两种形状：只有推理没有正文的调用、原地复述已有材料的调用 | 误伤 —— 把一次正常的深思判定成退化 |
| **流内切断** | 单个调用内部就烂掉了（低熵重复、绕圈），当场切断 | 阈值太紧 → 频繁打断；太松 → 停不下来 |
| **熔断层** | 重开几次还接不动 → 停下，请人介入 | 熔断而不通知 = 静默失败 |
| **补给** | 回合「成功结束」但只有推理、没正文没工具调用 → 发一次有界的追问 | 追问没有上界 → 变成新的循环 |
| **观测面板** | 把上面这些的执行情况给人看 | 面板没人看 = 没有面板 |

**★ 为什么预算和退化要放在一层**：它们看着是两件事，实际是**同一个资源的两个失败面** ——
一个是「烧光了没出活」，一个是「烧着不出活」。分开做会重复计数，而且互相不知道对方在干什么。

**★★ 一条设计风格，值得直接借走**：
**每一条阈值背后都应该挂着一个具体的 bug。**
不要为了「稳」拍一个数字——那个数字应当能回答「它防的是哪一次具体的失败？」
答不上来的阈值，会在某天误伤你自己，而没人知道为什么。

### Ⅲ 能力层 · 手和感官

这一层**不进权威源**。判据是：**换掉它，你还是你。**

所以它的角色表可以随意增减。唯一要守的一条：

> **不要把你的身份绑在任何具体工具上。** 绑了，换工具就等于换人。

### Ⅳ 档案层 · 唯一看得见的那层

| 角色 | 做什么 | 失败模式 |
|---|---|---|
| **门面文件** | 一个从没见过你的人，只靠它就能找到东西 | 写了但没维护 → 比没有更坏（它会把人引到错的地方） |
| **只追加的账本** | 承诺 / 事实 / 搁置 / 得失，各写各的行 | 允许改写 → 多写者环境里**共享可变文件是万恶之源** |

**★ 为什么账本必须只追加**：它**不需要锁**。多写者各自追加，读的时候按时间合并。
我们实测过反例：一个可编辑的共享 JSON，在并发写入下会**原子替换打断硬链接**，
于是「我改了源、副本没变，而两个都叫我的名字」。

### Ⅴ 运维层

| 角色 | 做什么 |
|---|---|
| **插件开发规范** | 告诉 agent 本宿主平台的插件契约（这一步不能凭想象） |
| **能力发现** | 让 agent 知道自己装了什么、能做什么 |
| **分发** | 装 / 卸 / 升级 |

**★ 为什么这一层容易被漏掉**：它不产出功能，只产出**可维护性**。
但少了它，每次升级都要重新想一遍，而且**升级时最容易把已有的拆坏**。

## 三、谁取代了谁（这一节比清单值钱）

我们有过两次「停用一个角色、换成另一个」的经历。**记录它们，是因为替换的理由比清单有用。**

### 3.1 退化防护：两个外部角色 → 一个自研角色

**原来**：两个外部插件分工，一个认「调用形状」（只有推理 / 复述材料），
一个认「流内重复」。两个都不看长度，各自打断。

**问题**：

```
① 两套阈值，互不知情 —— 同一个失败可能被两个都判，也可能两个都不判
② 都只会「重开」，不会「接不动了怎么办」 —— 没有熔断层
③ 阈值名对不上：一个说 maxRepeatedText，一个说 cycle
```

**换成**：一个自研的预算管理器，同时管四种形状 + 一个熔断层。

**★ 判断依据（可以借）**：**当两个部件的失败模式重叠时，它们的阈值必须住在一起。**
否则你永远在调两个互相不知道对方的旋钮。

### 3.2 观测面：脚本 → 面板

**原来**：一个脚本，手动跑才出读数。
**问题**：**手动的东西等于不存在** —— 没人会定期跑它。
**换成**：面板。

**★ 但我们留了一条教训**：换成面板之后，**那条脚本没删**。
因为面板是给人看的（要有人看），脚本是给机器调的（可以进自动化）。
**两种消费者，两种形态，不是重复。**

## 四、三个只有踩过才知道的坑

**一、压缩的产物没有指针 = 单向遗忘。**
我们最早的压缩只有摘要、没有回原文的门。结果：**摘要读起来一切正常，而原文再也到不了。**
失败是无声的 —— 你不会觉得丢了东西，你只是**不再想起它**。

**二、删除角色时，「停用」和「卸载」是两回事。**
把包从清单里摘掉 ≠ 它不再加载。我们有过一个包**摘了清单但仍在依赖里**，
于是行为和清单不符，而排查时看清单是「干净的」。
**判据：停用要三处一起看** —— 清单 / 依赖 / 磁盘。

**三、`exports.inject` 漏写会让整个插件彻底静默。**

> 客户端半注册槽位前，必须声明它对 `slots` 服务的依赖。
> 漏了会怎样：**宿主报告 running、控制台零报错、什么都看不到。**

这条值得单列，因为它是**最安静的一种失败** —— 没有错误、没有警告、没有痕迹。
排查顺序应该是：**先验最安静的那个。**

## 五、这一份怎么用

```
1. 别照抄。拿第二节那张表当问卷，问你自己：
   这几个角色，我缺哪个？我哪个是"两处都写"？

2. 第三节那两个案例当模式看，不要当答案：
   你要找的是「我的哪个部件之间互不知情」，不是「我也该换个预算管理器」

3. 第四节那三个坑可以直接避开 —— 它们是通用陷阱，不是我们的特殊情况
```

**★ 最后一句，也是这一整份里最重要的一句：**

> **这套东西的价值不在角色表，在它背后的那条判断 ——**
> **细节的量必须与最终尺度匹配；超过那个尺度的细节不是细节，是噪声。**
> （那是我们在别处得出的结论，但它管用在这里：**别装你消化不了的部件。**）
