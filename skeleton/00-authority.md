# 00 · 权威源册

> **这份文件是第 0 步。** 填完它，再动任何机制。
>
> 为什么不先建记忆就先填这个：只要你打算让 agent 跨会话记住任何东西，
> 你就得先回答「那份东西的**唯一**权威副本在哪」。答不上来，你后面建的每一样东西
> 都会变成第二份副本 —— 而两份副本冲突时，你会花大量时间对账，且永远不知道哪份对。

---

## 一、三条前提（先认同，再往下填）

| # | 前提 | 不认同的后果 |
|---|---|---|
| ① | **一个资源，只有一个权威源。** | 两处都写 = 双重记账。对账的时间会超过干活的时间。 |
| ② | **权威源只追加，不改写。** | 改写的权限意味着「历史可以被改写」，而你需要的是「知道发生过什么」。 |
| ③ | **冲突时，以权威源为准，不以摘要为准。** | 摘要一旦能压过原文，你的记忆就开始撒谎。 |

★ 三条里最硬的是 ①。**如果只能记住一句话：两处都写，等于两处都不算数。**

---

## 二、★★ 三种身份（这一节比那张表重要）

> 你在目录里看到的每一份文件，都只可能是三种身份之一。
> **把它们分清，比背一张权威源表有用得多。**

| 身份 | 回答什么 | 规矩 | 怎么认 |
|---|---|---|---|
| **权威** | 「现在是什么」 | 唯一、可写、可改 | 被明确指定过的那一份 |
| **衍生** | 「从权威算出来的」 | **必须可丢弃、可重建** | 索引、摘要、缓存、投影 |
| **沿革** | 「改过什么、被什么推翻过、证据在哪」 | **只追加，一字不删** | 名字里带 `-沿革` / `-修订` / 日期备份 |

★★ **一句话判据：**

> **你看到的不是「重复文件」，是「权威 + 衍生 + 沿革」。**
> 觉得有两份重复时，先问：这两份是哪种身份对哪种身份？

### 2.1 ★ 一份文件有两种读法

这是这套东西里最容易搞错的地方 —— **同一个主题下可能有两份文件，读法完全不同**：

| | **读物** | **账本 / 沿革** |
|---|---|---|
| 它回答 | 「**现在是什么样**」 | 「**改过什么、被什么推翻过、证据在哪**」 |
| 规矩 | **只留最新结论** —— 被推翻的不要再出现 | **只追加，一字不删** |
| 怎么认 | 文件名正常的那份 | 文件名带 `-沿革` 的那份 |
| 怎么用 | **信它** | ★ **它是证据，不是结论** |

★ **两份冲突时**：先看读物（那是现在的答案），再看沿革（那是它怎么变成现在这样的）。

★ **不要把读物做成账本，也不要把账本做成读物。**
读物里留着被推翻的旧结论 = 你会读到两个互相矛盾的"现在"；
账本里删掉旧结论 = 你失去了"曾经错过"的证据。

## 三、权威源表（填这里）

> 每一行是一种「稀缺资源」。**资源**指会满、会丢、会漂、会过期的东西 —— 不是功能。
> 常见的就四五种，不要为了显得完整而硬凑。

| 资源 | 唯一权威源 | 形态 | 位置 | 谁可写 | 谁可读 | 冲突时听谁 |
|---|---|---|---|---|---|---|
| 事件与承诺 | `<文件名 / 子系统名>` | `<append-only jsonl / 单一 md / sqlite>` | `<相对你工作区的路径>` | `<人 / 主导会话 / 任意会话>` | `<全部>` | `<这一行本身>` |
| 检索索引 | `<例如：一个可重建的派生层>` | `<必须可丢弃重建>` | `<...>` | `<重建者>` | `<全部>` | `<权威源>` |
| 容器状态 | `<...>` | `<...>` | `<...>` | `<...>` | `<...>` | `<...>` |
| `<再加一行你的>` | | | | | | |

**填表时的四个常见错误：**

- **把索引填成权威源。** 索引一定要能被丢掉重建。填成权威源，你就再也不敢删它，于是它涨到无法维护。
- **把「摘要」填进「形态」列。** 摘要永远是衍生品，不是源。
- **「谁可写」填了「所有人」。** 那等于没有权限模型，后面一定会有一次写坏。
- **漏了「冲突时听谁」。** 这一列空着，等于默认「谁后写谁赢」，而那不是你要的。

## 四、同一主题有多份时，看哪个（★ 冲突优先级）

**按这个顺序判，不要跳步：**

1. **被明确指定过权威的**（在指令文件、体系文件或某个清单里写明了）→ 按它指的
2. **在账本里有记录的** → **账本为准**
3. **带「沿革 / 修订沿革」字样的** → 那是**证据，不是结论**
4. **日期新的** → 通常更新，但**先看上面三条**

★ 第 4 条放最后，因为**「新的」不等于「对的」**。
最容易被忽略的是第 2 条：账本里有记录，说明那件事真的发生过；而某份文档可能只是当时的一个打算。

### 4.1 建一份「已确认」清单

**每确认一组关系，就记一行。** 这是这份文件里唯一会长大的部分：

| 主题 | 权威 | 衍生 / 沿革 |
|---|---|---|
| `<...>` | `<...>` | `<...>` |

★ 为什么值得记：**下次你（或者下一个接手的人）会再问一次同样的问题。**
不记，就要重新查一遍。

## 五、★ 副本规矩（一种高发的静默事故）

> 如果你有「一份内容，两个位置」的情况，这一节必须读。

**症状**：你改了 A，以为 B 也变了；实际上 B 没变。而两个都被当成"那份文件"。
更糟的是，如果它们**看起来**是硬链接、实际上是两个独立文件，你在编辑器里永远看不出区别。

**判据（一眼分辨）**：
- 硬链接：改任意一处，另一处同步变
- 副本：改一处，另一处**不动**，而且**不报错**

**规矩：**

1. **定一个主**（写在权威源表里），其余的明确标为副本。
2. **要改只改主**，然后把主复制过去。
3. **改完核对**（哈希相等 / 内容 diff 为空）。
4. ★★ **绝不同时改两边。**

★ 第 4 条不是洁癖。**同时改两边，必然会在某一次漏掉一边 —— 而那次恰好是你最需要准确的时候。**

## 六、写入门（谁能往权威源里写）

> 这一节防的是「一个临时拉起的小 agent 替你签了一张承诺」这类事故。

| 写入者 | 能写什么 | 不能写什么 | 怎么识别它 |
|---|---|---|---|
| **人** | 全部 | — | — |
| **主导会话**（替人做承诺的那一个） | 全部 | — | `<一条可执行的判定，例如：查某条记录，看最后一条的署名是不是本会话>` |
| **执行会话**（被拉起干活的） | `<例如：事实 / 搁置 / 得失>` | `<例如：承诺 / 升任>` | `<...>` |
| **定时任务** | `<...>` | `<...>` | `<...>` |

★ **「不能写什么」最好由代码拦，不要靠自觉。** 自觉会疲劳，代码不会。
如果你的写入接口有退出码，让越权的写入**直接失败**，而不是写进去再打日志。

## 七、唯一性自检（怎么证明你没违反前提 ①）

- [ ] **列出所有会落盘的地方**（除了权威源）：`<...>`
- [ ] 对每一个，回答：**它能不能被删掉并从权威源重建？**

      - 不能 → **它是第二个真源**，要么合并，要么明确它不是权威的
- [ ] **找一个"如果我同时改两处，会怎样"的例子**，写在这里：`<...>`
- [ ] 你的检索工具能不能**指回原文**（而不是只返回摘要）？`<能 / 不能，为什么>`
- [ ] 你所有的「副本」都标出来了吗？改的时候只改主了吗？

★ 最后一条之前那条最重要：**拿不回原文的索引，等于一个新的真源。**

## 八、留白（这一节故意不填）

下面这些问题**没有标准答案**，而且答案会随你的用法变化。留着，等你用了一个月再回来填：

```
我最初以为权威源是 ______，一个月后发现实际上每次读的都是 ______。

我填错的一行是 ______，症状是 ______。

我发现的第一处漂移是 ______，它漂了 ______ 天。
```

★ 保留这一节的原因是：**这份表的价值不在填得漂亮，在于它被现实修正过一次。**
一份从没被改过的权威源表，通常意味着它从来没被真正用过。
